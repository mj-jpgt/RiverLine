## 1. Loose end: `scripts/db/migrate.mjs` TOCTOU race

Flagged by T-C6/C7: two concurrent `applyMigrations()` calls against the
same database both read `schema_migrations`, both see the same file
pending, both try to apply it — a real race under parallel vitest workers
or a multi-replica rolling deploy.

**Fix**: a Postgres session-level advisory lock (`pg_advisory_lock` /
`pg_advisory_unlock`) around the whole migrate run, fixed key
`9142_0817_001n`, held on its own connection for the duration. A second
concurrent caller blocks (doesn't fail) until the first finishes, then
re-reads `schema_migrations` after acquiring the lock (not before — a
concurrent caller may have already applied what looked pending) and finds
nothing left to do. Forward-only semantics unchanged — no down-migration
machinery added.

**Proof**: `test/unit/ops/migrate-lock.test.ts` — two real concurrent
`applyMigrations()` calls against a fresh scratch database
(`riverline_migrate_lock_test`), both resolve without error, every
migration recorded in `schema_migrations` exactly once (`GROUP BY filename`
count == 1 for every row). Passed both in isolation and as part of the full
293-test suite.

## 2. Loose end: mobile-safari magic-link flake

Read T-C1/T-C2/T-C3/T-C4's journals first. Documented root cause:
`src/core/auth/dev-link-store.ts` held **one "most recent" pending link per
email** in a `globalThis` Map. Playwright runs `fullyParallel` across the
`chromium` and `mobile-safari` projects, and six spec files
(`login.spec.ts`, `registry.spec.ts`, `calculation.spec.ts`,
`a2-dashboard.spec.ts`, `determination.spec.ts`, `a1-letters.spec.ts`) all
request a magic link for the same seeded demo email
(`assessor@example.gov`) and immediately fetch it back via the dev-only
route. A second concurrent `setDevMagicLink` call for the same email used
to overwrite the first entry before it was read — so two different
callers' `getDevMagicLink` could return the **same single-use token**.
Whichever test navigated to it second got an already-consumed token
(`login_tokens.used_at` already set) and failed to reach `/home`.

**Fix**: a per-email FIFO queue instead of a single slot. Every
`setDevMagicLink` enqueues a new entry; every `getDevMagicLink` dequeues
(and removes) the oldest still-valid one. Verified every call site in this
codebase does exactly one request-then-fetch pair per test (no
polling/retry), so this is safe: however many concurrent requesters are in
flight for one email, each `getDevMagicLink` now returns a distinct,
never-before-returned token, in any interleaving order.

**Proof, three layers**:

1. **Unit** (`test/unit/ops/dev-link-store-race.test.ts`, 5 tests, no
   HTTP/browser): concurrent `set()` calls produce distinct entries, not an
   overwritten one; 25 interleaved requesters each get a distinct
   never-repeated token; FIFO order; expired-entry pruning; per-email
   isolation. All pass deterministically.
2. **HTTP integration** (ad hoc script, not committed — see "What wasn't
   committed" below): 4 concurrent real `POST /api/auth/request-link` +
   `GET /api/dev/magic-link` pairs against a real running `next dev`
   server for the same seeded email. Result: **4/4 distinct tokens
   returned, 4/4 independently verified successfully** (each redirected to
   `/home` via the real `/api/auth/verify` route, consuming a real
   `login_tokens` row). N was kept at 4, under the 5-per-15-min
   `EMAIL_LIMIT` W3's concurrent security-hardening pass added to
   `app/api/auth/request-link/route.ts` — an unrelated new rate limit that
   a naive higher-N stress run tripped (429), which is correct behavior
   from that route, not a bug.
3. **Browser** (Playwright, `mobile-safari` project) — see "A second,
   different flake was found" below; the original duplicate-token failure
   mode did **not** reproduce anywhere once the fix landed. A different,
   pre-existing WebKit issue did.

## 3. Working on a live shared tree (methodology note)

`next dev` watches the whole project directory. With three other agents
concurrently editing files in this same working tree, an in-flight e2e run
would intermittently hit React Fast Refresh full reloads mid-navigation, or
build errors from another agent's not-yet-complete module (e.g. an early
Docker build failed on `Module not found: './EstimateUploadFlow'` — W2's
A4 module mid-write, not a defect in anything committed).

Two mitigations used throughout, both non-destructive to other agents'
work:

- **Docker build/compose prove-out**: built from `git worktree add
  ../riverline-w4-build 013517f` (a separate, isolated checkout at the last
  stable integration commit) with only this task's own changed files
  copied in — not the live, actively-mutating tree. This is what "docker
  build the image for real" below is proven against.
- **e2e root-cause isolation**: when a live-tree mobile-safari run showed a
  failure mode that didn't match the documented flake, the same isolated
  worktree (plus a port-remapped Playwright config, since the shared root
  config is hardcoded to `localhost:3000` and another agent already had a
  dev server bound there) was used to rule out concurrent-agent file churn
  as the cause. See below.

Both were torn down / removed at the end of the session; nothing here
persists as an artifact in the repo.

## 4. A second, different flake was found (not fixed — out of scope)

Running the full root e2e suite against the live tree surfaced a **new**
failure mode on `mobile-safari` only:

```
Error: page.goto: Navigation to ".../api/auth/verify?token=..." is
interrupted by another navigation to ".../login"
```

This is a **different** symptom from the documented dev-link-store race
(which produced "lands on /login instead of /home" via a normal, completed
navigation to an already-used token — not a Playwright-level "navigation
interrupted" error). Investigated properly rather than assumed:

1. Ran a **single** `login.spec.ts` test, `--workers=1`, no repeat, no
   concurrency of any kind possible → **still failed, 100% reproducible.**
   This rules out any request-level race (including the one this task
   fixed) as the cause — there is no second concurrent requester in this
   scenario.
2. Ran the same test in the **isolated worktree** (pinned to `013517f` +
   only this task's own file changes — no W1/W3 changes present at all,
   no concurrent file edits possible) → **still failed, reproducible on
   two separate runs.** Rules out both concurrent-agent file churn and
   W3's new middleware/rate-limiting as the cause.
3. Ran the **same isolated worktree, same flow, `chromium` project** →
   **7/7 passed cleanly.** The failure is WebKit-specific, not a logic bug
   reachable from any browser.

**Working hypothesis** (not confirmed with a network trace — would need
more time than this task had): WebKit appears to issue the navigation to
the single-use `/api/auth/verify?token=...` URL more than once under some
condition (possibly slow server response under this session's heavy
concurrent system load — four agents' worth of Node/Docker/browser
processes on one machine). If a first, Playwright-invisible request reaches
the server and consumes the token (`login_tokens.used_at`) before a second
request/retry is sent, the second gets `verifyMagicLink() -> null` and
redirects to `/login` — exactly the observed symptom. This machinery
(`verifyMagicLink`, single-use token consumption) is unrelated to the
dev-link-store fix in this task; changing single-use-token semantics to
tolerate this would be a real security-relevant behavior change and wasn't
made here without being sure of the actual cause — per AGENTS.md's "ask
before guessing," this is flagged for a follow-up task with time to attach
a HAR/network trace, not guessed at.

**This is pre-existing, not introduced by this session's work**: the
orchestrator's own `2026-08-17-integration.md` (commit `013517f`, before
any of this session's changes) already lists "root e2e chromium — PASS,
14/14" but does not claim a clean mobile-safari root-suite run, and
separately lists "Mobile-safari magic-link flake... does not affect
chromium suites" as an open item — consistent with mobile-safari already
being unreliable at that commit for reasons broader than the single
dev-link-store bug this task was scoped to.

## 5. Production container (`Dockerfile`, `docker-compose.prod.yml`)

`output: 'standalone'` would need one line in `next.config.ts`, which is
W3's file this wave and off-limits. Built instead against the plain `next

diff in `docs/deploy/self-host.md` → "Known follow-up."

Two real bugs found and fixed while getting a real `docker build` green
(not assumed correct — see the numbers below):

1. `.dockerignore` originally excluded all of `docs/`, but
   `app/globals.css` does `@import "../docs/design/tokens.css"` at build
   time — excluding it broke `next build` inside the image with a real
   webpack resolution error. Fixed by excluding `docs/` subdirectories
   individually instead of the whole tree, keeping `docs/design/tokens.css`
   (and the whole `docs/design/` folder, in case of future CSS assets)
   available to the build.
2. `pnpm prune --prod` in the runner stage removed `typescript` — but
   `next start` transpiles `next.config.ts` (a `.ts` file) **at boot**, not
   only at build time, and needs `typescript` present to do that. Pruning
   it caused a real container boot failure
   (`ERR_PNPM_UNEXPECTED_STORE`, from `next start` trying to
   self-install `typescript` at runtime as the non-root user against a pnpm
   store owned by the root-run build stage). Fixed by shipping the full
   `node_modules` (prod + dev deps) in the runner stage instead — larger
   image, but boots correctly. `output: 'standalone'` (the documented
   follow-up) would avoid this whole class of problem by shipping a
   pre-transpiled config.
