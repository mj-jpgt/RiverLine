# 2026-08-18 — T-V2: pluggable production email transport (magic-link)

## What I did

- **Research first, per the task brief.** Compared three transactional
  email options for magic-link delivery to jurisdiction officials
  (plausibly on strict institutional/`.gov` mail systems): Postmark,
  Resend, and AWS SES's raw HTTPS API. Full comparison, primary-source
  citations with retrieval dates, and the decision trail are in
  `docs/adr/0009-email-transport.md`. Short version: **Postmark**, because
  its product is specifically built around transactional deliverability
  (a dedicated `outbound` stream, never shared reputation with bulk mail),
  its free plan (100/month, no credit card, never expires) has DKIM/domain
  verification on every tier including free, and its plain-JSON/single-
  header API is exactly as `fetch`-friendly as Resend's. AWS SES's raw API
  requires hand-rolled AWS SigV4 request signing — AWS's own docs call
  that "a complex undertaking" and recommend the SDK — which would have
  meant either a new dependency or a nontrivial custom signing
  implementation inside an auth-adjacent path; rejected on that basis
  alone, independent of SES's actual deliverability.

- **`src/core/auth/email-transport.ts` (new).** Pluggable transport,
  driver selected by `EMAIL_DRIVER`:
  - `"dev"` — logs the link and stashes it in the existing
    `dev-link-store` for the dev-only retrieval route, byte-for-byte the
    same behavior `magic-link.ts` used to inline. Structurally cannot run
    when `NODE_ENV=production`: `resolveEmailDriver()` throws if `"dev"`
    is selected (explicitly or by misconfiguration) in production, and
    `sendMagicLinkEmail()` re-checks before logging, matching
    `dev-link-store.ts`'s own "defense in depth" pattern for the same
    class of mistake.
  - `"http"` — POSTs to Postmark (`https://api.postmarkapp.com/email`)
    via the runtime's global `fetch` — **zero new npm dependencies**
    (AGENTS.md rule 3). Provider URL/key/from-address are entirely
    env-driven (`EMAIL_API_URL`, `EMAIL_API_KEY`, `EMAIL_FROM`), never
    hardcoded. `buildPostmarkPayload()` is exported and pinned by an
    exact-JSON unit test so email-content edits can't silently drift from
    what Postmark's API actually expects.
  - `"none"` — throws a clear, loud error. Default when `EMAIL_DRIVER` is
    unset **and** `NODE_ENV=production` — this is the same behavior
    `magic-link.ts` used to inline directly; moving it into
    `email-transport.ts` didn't change its shape, only its location. Never
    a silent no-op.
  - Email content: mandatory plain-text part (institutional tone, the
    link, "expires in 15 minutes," "if you did not request this, ignore
    this email" — no marketing, no images) plus a simple optional HTML
    part (also no images, no tracking). The HTML body deliberately uses
    named CSS colors (`black`/`white`), not hex — this is email-client
    HTML that `docs/design/tokens.css` structurally cannot reach (no
    stylesheet link survives most email clients), and this repo's
    `riverline/no-raw-color-or-arbitrary-value` lint rule correctly
    doesn't special-case this file, so named colors are the honest way to
    satisfy both the lint rule and cross-client email compatibility rather
    than working around the rule.
  - Security: `APP_BASE_URL` builds the absolute link mailed to a real
    inbox (dev mode never needed one — the dev route just returns a
    relative path, unchanged); validated to start with `https://` when
    `NODE_ENV=production`. The raw token only ever reaches (a) the
    dev-only console log/store, unreachable in production, or (b) the
    outbound HTTPS body sent directly to Postmark — no thrown error or log
    line in the `"http"`/`"none"` paths ever contains the token or the
    full verify URL (unit-tested explicitly). Rate limiting already exists
    upstream (`app/api/auth/request-link/route.ts`,
    `src/shared/security/rate-limit.ts`) and is not duplicated here.

- **`src/core/auth/magic-link.ts`** — minimal edit: the inline

  call, `await sendMagicLinkEmail({ email, verifyPath, expiresAt })`. No

- **`.env.example`** (additive only) — documents `EMAIL_DRIVER`,
  `EMAIL_API_URL`/`EMAIL_API_KEY`/`EMAIL_FROM` (with the exact Postmark
  values/where to get the key), and `APP_BASE_URL`.

- **`docs/BLOCKERS.md` B4** — updated from "blocked" to "CODE READY — needs
  provider API key," with the exact remaining human steps (Postmark

## What I had to debug (real findings, not assumptions)

1. **`NODE_ENV` is `readonly` in this project's TypeScript types.**
   Next.js's own global type augmentation declares
   `NodeJS.ProcessEnv.NODE_ENV` as `readonly 'development'|'production'|
   'test'`, which correctly blocks accidental production-env mutation in
   app code — but this test suite legitimately needs to flip it between
   `"test"` and `"production"` to exercise both branches of
   `resolveEmailDriver()`/`sendMagicLinkEmail()`. Fixed by routing the
   mutation through a differently-typed reference
   (`process.env as unknown as Record<string, string | undefined>`) inside
   the test file only — defeats the type-level guard in this one file,
   never a runtime guard, and never touches app code.
2. **This repo's `riverline/no-raw-color-or-arbitrary-value` ESLint rule
   applies to every file under `src/**/*.{ts,tsx}`, including a raw HTML
   string used as an email body**, and correctly flagged
   `color:#111;background:#fff` in the HTML email template as a raw hex
   color. Not a rule bug — this file genuinely isn't part of the app's
   design-token system, but the rule has no reason to know that. Fixed
   honestly (named CSS colors `black`/`white`, appropriate for
   cross-client email HTML anyway), not by suppressing the rule.
3. **Running Playwright against the live shared working tree produced a
   100%-reproducible false failure** (`toBeEnabled()` timeout on the
   submit button after `pressSequentially`, with `Fast Refresh had to
   perform a full reload due to a runtime error` in the webServer log) —
   the same class of issue T-W4's journal documented
   (`docs/journal/2026-08-17-w4-deploy.md`): three other concurrently
   running agents (W5/V1/V3) are actively rewriting dozens of files in
   this shared, non-isolated working tree, and `next dev`'s file watcher
   reacting to that churn interrupts in-flight navigations. Root-caused by
   first reproducing it against the shared tree on port 4200 (failed), then
   reproducing the identical login/smoke run against an isolated
   `git worktree` pinned to the last commit with only this task's own
   changed files copied in (passed cleanly, 3/3, twice). Verified the
   worktree approach for real rather than assuming — see "Acceptance
   checks" below for the actual commands and output.
