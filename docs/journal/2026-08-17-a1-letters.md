# 2026-08-17 — T-A1: determination letters, honest refusal state

## What I did

Built A1 end to end: the "Generate letter" surface for an adopted
determination, whose headline behavior is refusing explicitly when
`jurisdictions.ordinance_citation` is null — which is the real state of
every jurisdiction in this codebase today (verified again this session:
`docs/data-contracts/ordinance-citations.md` is still BLOCKED, Cloudflare
bot protection defeats automated retrieval; `docs/BLOCKERS.md` B2 is a
human-only blocker, not something this task could resolve).

- **`src/modules/a1-letters/`** (my module directory):
  - `types.ts` — `LetterFacts`, `LetterPreviewResult` (a closed set of
    explicit states: `not_found` / `no_determination` /
    `borderline_unresolved` / `citation_missing` / `ready` / `issued`),
    `IssueLetterResult`, `SetOrdinanceResult`.
  - `pure.ts` — zero-I/O: `buildLetterFacts` (formats raw DB rows into
    display-ready facts, never fabricating an optional field),
    `renderLetterHtml` (the full standalone print-first HTML document —
    SD/NOT_SD variants, conditional appeal sentence, conditional ICC
    paragraph, mandatory footer, preview banner), `TEMPLATE_VERSION`,
    `MANDATORY_FOOTER_TEXT`, `isNonEmptyOrdinanceCitation`,
    `isValidAppealWindowDays`.
  - `queries.ts` — `getLetterPreview` (the single source of truth for which
    of the six states applies, jurisdiction-scoped via `withTenant`/RLS),
    `readArchivedLetterHtml`.
  - `actions.ts` — `issueLetter` (re-validates state server-side, writes
    the archived HTML to `uploads/letters/<jurisdictionId>/<letterId>.html`,
    INSERTs the immutable `letters` row, links
    `determinations.letter_id`, audits), `setOrdinanceCitation`
    (admin-only path that writes `jurisdictions.ordinance_citation` +
    `letterhead_config.appeal_window_days`/name/address lines, audited
    before/after on the jurisdiction row).
  - `index.ts` — the module's only public surface, per
    `docs/adr/0003-module-boundary-enforcement.md` (`src/modules/<x>` may
    only be reached through its `index.ts`).

- **`app/letters/[clientId]/`** (my route directory — kept to exactly this
  path, per the task's coexistence rules; no `app/api/letters/` was
  created):
  - `page.tsx` — the six states, each designed (never a blank area): the
    refusal panel is the most visually prominent thing this page can show
    (`.refusalPanel`, 2px SD-colored border), quoting `docs/BLOCKERS.md`
    B2 by name and offering the admin-only `OrdinanceForm` inline, or a
    "ask an administrator" message for everyone else. The `ready`/`issued`
    states embed the print route in an `<iframe>` as a live preview.
  - `_components/OrdinanceForm.tsx` — admin-only citation + appeal-window
    form. Starts empty (no placeholder that could be mistaken for a real
    citation); blocks an empty submit with a designed inline error.
  - `_components/IssueLetterAction.tsx` — two-step confirm (same pattern
    as `app/determination/[clientId]/_components/AdoptAction.tsx`) — issuing
    is not meaningfully reversible.
  - `ordinance/route.ts` — `POST`, admin-only (`requireRole(["admin"])`).
  - `issue/route.ts` — `POST`, admin/official (`requireRole(["admin",
    "official"])`), same role set as determination adoption.
  - `print/route.ts` — `GET`, any authenticated role; serves the archived
    HTML byte-for-byte once issued, or a live preview (with a
    screen-only, non-printing banner) beforehand; a plain 404/401/403 text
    response for every other state — never renders a letter for anything
    but a ready/issued determination.
  - `loading.tsx` / `not-found.tsx` / `error.tsx` — every state shipped,
    mirroring `app/determination/[clientId]`'s pattern exactly.

- **`docs/adr/0006-letter-rendering.md`** — chose (a) print-CSS HTML +
  browser print-to-PDF over (b) server-side PDF via the already-installed
  Playwright chromium. Zero new production dependency (Playwright is a
  devDependency; promoting it to the request path would be an undocumented
  production cost — a full Chromium binary — and its own ADR/dependency
  decision, out of scope here). Documents the load-bearing naming mismatch
  honestly: `letters.pdf_storage_key` (frozen schema column) stores HTML in
  this MVP, never presented as a PDF in UI copy (the only PDF-adjacent
  string anywhere is the "Print / Save as PDF" button label, describing
  what the browser's print dialog does).

## THE headline feature — refusal state, proven three ways

1. **Unit** (`test/unit/modules/a1/persist.test.ts`, real Postgres): a
   freshly seeded jurisdiction with `ordinance_citation` left `NULL` (the
   real, honest default — same as `scripts/db/seed.mjs`, never touched by
   this test) produces `getLetterPreview(...) === { status:
   "citation_missing" }` for an adopted, definite determination, and
   `issueLetter(...)` refuses (`not_ready`) without creating any `letters`
   row (asserted via a before/after row-count query).
2. **Unit** — `borderline_unresolved` and `no_determination` are also
   covered as their own explicit, non-fabricated states — a letter is
   never rendered for a BORDERLINE ratio (no SD/NOT_SD sentence would be
   honest) or a determination that isn't currently `adopted`.
3. **E2E** (`test/e2e/a1-letters.spec.ts`, real browser, real Postgres,
   real dev server): an assessor captures and syncs a real 25%-uniform-damage
   assessment on the seeded "123 Practice Ln" practice structure (same
   recipe `test/e2e/determination.spec.ts` verified produces a definite
   NOT_SD ratio — 0.2444, clear of the borderline band), an official
   adopts it via the real UI (two-step confirm), then `/letters/[clientId]`
   is loaded and asserted to show "Letter generation unavailable", the
   `docs/BLOCKERS.md` citation, and the admin form — with a DB query
   before/after proving zero `letters` rows were created. A separate test
   proves the role guard: an authenticated assessor (real session cookie,
   `page.request` so it's not just unauthenticated) gets 403 from both
   `POST /letters/[clientId]/ordinance` and `POST
   /letters/[clientId]/issue`.

## What the rest of the e2e spec proves

- An admin fills in `OrdinanceForm` with an obviously-synthetic fixture
  citation (`"TEST ORDINANCE §00-000 — fixture, not legal text"`) — the
  refusal state clears, the `<iframe>` preview renders that exact text
  verbatim plus the `IS NOT substantially damaged` finding sentence, and
  `audit_log` gets a `jurisdiction`/`set_ordinance_and_letterhead` row.
- Issuing creates the permanent record: `letters` row (`pdf_storage_key`
  starting `letters/`, `issued_at` set), `determinations.letter_id`
  linked, one `audit_log` row (`entity_type='letter'`, `action='issue'`).
- `page.emulateMedia({ media: 'print' })` against `/letters/[clientId]/print`
  (which by this point serves the *archived* copy, read back from disk)
  asserts `getComputedStyle(document.body)` is exactly `rgb(0, 0, 0)` on
  `rgb(255, 255, 255)` — literal black-on-white per `docs/design/direction.md`
  → "Print" — and that the preview banner (screen-only chrome) is absent
  from the printed/archived document.

## Deviations / honest gaps

- **No "Generate letter" link exists on `app/determination/[clientId]`.**
  That file is outside my module directory (owned by T-C5/core, not listed
  in my allowed paths) and I did not touch it. `/letters/[clientId]` is
  fully functional and reachable directly by the same `clientId` URL
  convention `/calculation/[clientId]` and `/determination/[clientId]`
  already use — an official can navigate there directly, or a future task
  inside `app/determination/`'s own module can add the link. Flagging
  this explicitly rather than reaching outside my assigned directory.
- **"Official's name"** — `schema/core.sql`'s `users` table has no name
  column, only `email`. The letter's signature block honestly labels this
  "Adopting official: `<email>`" rather than inventing a display name.
- **ICC paragraph** — `letterhead_config.icc_text` is read and rendered
  verbatim if a jurisdiction has supplied it, entirely omitted otherwise.
  No admin-form field writes `icc_text` in this task (the task's required
  admin-form scope was citation + appeal window days specifically); a
  jurisdiction-supplied ICC paragraph can currently only be entered by a
  direct DB write. Noting this as an open item rather than authoring any
  ICC boilerplate text myself (forbidden — "never generate ICC prose").
- **Letterhead name/address** — `OrdinanceForm` does not currently expose
  fields for `letterhead_name`/`address_lines` (the action function
  `setOrdinanceCitation` accepts them, but the form UI only wires citation
  + appeal window, the two fields the task named explicitly). Until set,
  the letterhead block falls back to the jurisdiction's real `name` column
  with no address lines — never a fabricated address.
- **Re-issue / amend flow is out of scope.** Once a letter is issued,
  `IssueLetterAction` is not shown again (`issued` state has no "re-issue"
  button). A corrected letter after a `supersede` would need a new task —
  noting this rather than quietly building an ambiguous overwrite path for
  a legally consequential document.
- **`docs/adr/0006` naming mismatch** — `letters.pdf_storage_key` (frozen
  column name) stores HTML, not PDF bytes, in this MVP. Documented at
  length in the ADR; never described as a PDF anywhere in this module's UI
  copy.

## Test harness note (why the e2e run isn't a single `pnpm` command)

My task's environment notes restrict me to typecheck/lint/my isolated unit
suite/my own e2e spec against a dev server I start myself on port 3400,
never touching ports 3000/3100/3200/3300, and writing only inside my
listed paths (which does not include a new `playwright.*.config.ts` at the
repo root — that space is `playwright.config.ts`/`playwright.determination.config.ts`,
outside my paths). I ran the e2e spec via an ephemeral Playwright config
kept entirely in my own agent scratchpad (outside the repo tree, never
written into any repo path), importing `@playwright/test` by absolute
path (Node's ESM bare-specifier resolution has no `node_modules` ancestor
outside the repo, so a relative/bare import from that location fails —
confirmed by hitting `ERR_MODULE_NOT_FOUND` twice before switching to the
absolute-path import). The recipe, reproducible by any future agent:

1. `node scripts/db/seed.mjs --test` (seeds riverline_test's Demo City +
   demo users + practice structure — idempotent, already existed from a
   prior session's runs; confirmed `ordinance_citation` is `NULL` and a
   `TEST-FIXTURE` `cost_tables` row scoped to Demo City already exists from
   T-C5's own gate, so no new cost table needed to be inserted).
2. Start `next dev -p 3400` with `DATABASE_URL` pointed at
   `.../riverline_test` (detached, log redirected).
3. `playwright test --config=<scratchpad>/playwright.a1.config.mjs`, with
   `A1_BASE_URL=http://localhost:3400` — the spec uses this absolute base
   URL directly (`page.goto`, `page.request.post`) rather than relying on
   a config's `use.baseURL`, so no shared `playwright.config.ts` fields
   are needed at all.
4. Kill the dev server; confirmed port 3400 free afterward
   (`Get-NetTCPConnection -LocalPort 3400 -State Listen` — empty).

One real bug this surfaced and fixed, twice: my first spec draft assumed
Playwright's `page` fixture (and session cookie) carries over between
`test(...)` blocks in a `serial` describe — it does not; each test gets a
fresh browser context. Tests 2, 5, and 6 originally reused whatever
context test 1 or 4 left behind and either got redirected to `/login` or
hung waiting for a control that was never on a blank page. Fixed by
calling `loginViaDevMagicLink` again at the top of every test that needs
an authenticated page — the same discipline
`test/e2e/determination.spec.ts` already follows, which I should have
copied exactly the first time instead of assuming shared state.

A second real bug: the role-guard test's first draft asserted 403 using
the bare `request` fixture, which is an unauthenticated context separate
from the page's cookie jar — got 401 (no session), not 403 (wrong role).
Fixed by using `page.request` (shares the page's cookies) — the same
distinction `test/e2e/determination.spec.ts`'s own
`loginAsAssessorAndAttemptAdopt` helper (using `context.request`) already
demonstrates.

A third: my second full run of the suite failed test 2 because a *prior*
run had already set Demo City's `ordinance_citation` (test 4 of that
earlier run), and jurisdiction state persists in the DB across separate
e2e invocations — unlike a fresh `riverline_test` seed. Fixed by resetting
`ordinance_citation`/`appeal_window_days` back to `NULL`/unset for Demo
City in `beforeAll`, so the refusal assertion reflects the real default
regardless of how many times this spec has run before. This module is the
only code path that ever sets `ordinance_citation`, so the reset cannot
affect any other concurrently-running agent's fixtures (T-A2/T-A3 use
their own uniquely-timestamped jurisdictions; T-C5's own gate never
touches `ordinance_citation`).
