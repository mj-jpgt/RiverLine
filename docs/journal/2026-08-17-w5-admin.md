# 2026-08-17 — T-W5: admin console (cost tables, jurisdiction settings, readiness)

## The problem

The orchestrator found, while walking through the app as a real user, that
`cost_tables` is READ by the engine (M3) but nothing anywhere WRITES it
except test harnesses (`scripts/test-determination.mjs`,
`test/unit/*/persist.test.ts`). On a real deployment the 50%-rule
calculation could never run: every assessment dead-ends permanently at the
honest "no cost table loaded" state (`docs/BLOCKERS.md` B1). The same shape
of gap existed for jurisdiction configuration: `ordinance_citation` had a
form bolted onto `app/letters/[clientId]`, but appeal-window days and
letterhead config had no standalone UI, and there was no single page
telling a new jurisdiction what it still needs to configure.

This task builds `/admin` (admin role only): a readiness panel, cost-table
management (the critical piece), and jurisdiction settings — the way a real
jurisdiction resolves both gaps itself, without a DBA.

## How the ACTIVE cost table is selected — matched, not changed

`app/calculation/_lib/compute.ts` already has an explicit, documented rule
(no `active` flag exists in the frozen schema): prefer a jurisdiction-scoped
`cost_tables` row over a shared/global one (`jurisdiction_id is null`),
then the most recently effective `effective_date` within that preference.
This was NOT ambiguous, so `src/core/admin/queries.ts`'s
`queryActiveCostTableVersion` mirrors that exact SQL (documented inline as
intentionally coupled to `compute.ts`'s query — if that query ever changes,
this one must change with it) rather than inventing a second rule. The
admin cost-table list's ACTIVE badge is therefore always the same row a
real calculation would use.

## src/core/admin vs src/shared/admin

The task offered a choice. `src/core/admin` was chosen because this module
holds real business logic and SQL — validation rules, the ACTIVE-table
tie-break, jurisdiction-settings read/merge/audit — the same shape as
`src/core/determination` and `src/core/registry` (domain queries +
mutations behind an `index.ts`), not a dependency-free presentational/
utility leaf like `src/shared/ui` or `src/shared/db`. `src/shared/**` never
imports `src/core/*` in this codebase (it is a boundary leaf) and has no
precedent for holding tenant-scoped SQL; putting DB queries there would be
the first exception to that pattern.

## The parallel jurisdiction-settings endpoint

`app/letters/[clientId]/ordinance/route.ts` (built by an earlier agent,
backed by `src/modules/a1-letters`'s `setOrdinanceCitation`) is left
COMPLETELY untouched — not one line changed. `src/modules/a1-letters` is
outside this task's assigned module directories, and the task instructions
explicitly offered "reuse/refactor-in-place… otherwise a parallel admin
endpoint." A parallel endpoint was chosen: `app/api/admin/jurisdiction/
route.ts` → `src/core/admin`'s `updateJurisdictionSettings`, which owns the
SAME `jurisdictions.ordinance_citation` column and the SAME
`letterhead_config` sub-keys the letters module already reads
(`appeal_window_days`, `letterhead_name`, `address_lines`, `icc_text` —
confirmed by reading `src/modules/a1-letters/queries.ts`'s
`readAppealWindowDays`/`readLetterheadName`/`readLetterheadAddressLines`/
`readIccText`). Because eslint-plugin-boundaries forbids a `core` family
from importing a `modules` family, these tiny key-reading helpers are
duplicated as 3-line pure functions in `src/core/admin/queries.ts` rather
than imported — not a domain fact, just a JSON-shape reader.

One real behavioral difference from the existing bolted-on form: the admin
screen supports GENUINE field clearing. `setOrdinanceCitation` only ever
ADDS a `letterhead_config` key (passing `null` for `appealWindowDays` means
"leave whatever is already there alone"). The admin screen's
`updateJurisdictionSettings` treats an explicitly blank field as "unset" —
it deletes the key from `letterhead_config` — matching this task's
instruction verbatim ("empty = unset = appeal_deadline_date stays null").
Both endpoints still write mutually-compatible data (same table, same
column, same keys), so `app/letters` continues to read correctly no matter
which path last wrote a given jurisdiction's settings; this is proven by
`test/e2e/admin.spec.ts`'s final test (admin sets the citation via
`/admin/jurisdiction`, official adopts, `/letters/[clientId]` renders the
citation with no code changes to the letters module) and by re-running the
untouched `a1-letters.spec.ts` gate (see Acceptance below).

## Cost-table validation choices (documented, not invented facts)

- **20-character minimum source citation.** Not a sourced fact — a
  placeholder-guard so a single word ("guide", "n/a", "TBD") cannot pass,
  chosen so a real citation ("Marshall & Swift Residential Cost Handbook,
  2026 ed., p. 42" — 57 chars) clears it comfortably. Documented in
  `src/core/admin/pure.ts` next to the constant. This does not replace
  human review of the citation's actual content.
- **Zero is an accepted dollar value**, not just positive numbers — an
  element genuinely priced at $0/sqft by a real cost guide is a legitimate
  (if unusual) operator input; rejecting it would be inventing a rule FEMA
  P-784 does not state. Negative and non-finite values are rejected.
- **Extra/unknown element codes are rejected outright** (zod `.strict()`
  at both the residential and non-residential level), not silently
  ignored — an unrecognized code would never be read by the engine (it
  validates element codes against the cost table's own key set), so
  accepting it would let a form look "saved" while quietly doing nothing
  at calculation time.
- **`cost_tables.version` is the frozen schema's primary key**, global
  across jurisdictions (not composite with `jurisdiction_id`). A duplicate
  version label — even for a different jurisdiction — is rejected with a
  clear `version_exists` error (caught from the Postgres unique-violation,
  code `23505`) rather than surfacing a raw 500.

## Debugging note: shared `next dev` / `.next` contention (worth recording)

The admin e2e gate took many iterations to get green, and it's worth being
honest about why, since none of the root causes were in this task's own
application code:

1. **Environment drift mid-task.** The task briefing said "you are the
   ONLY agent running." That was not true in practice — a large,
   unrelated concurrent motion/animation polish pass (commit `404ab78`,
   "V3: motion pass") landed across nearly every `app/**` file while this
   task was in flight, and the orchestrator's own port map was stale
   relative to reality (port 3000 turned out to be an unrelated app,
   `telo-web`; the user's real Riverline dev server was on port 3001, not
   3000). None of this was discoverable from the task brief alone —
   diagnosed empirically via `Get-CimInstance Win32_Process` command-line
   inspection.
2. **Shared `.next` build directory.** Every `next dev` process pointed at
   this repo (mine on 3900, the user's on 3001, and at least one other
   transient instance seen on port 4100 during the session) writes to the
   SAME `<repo>/.next` directory. Two or more `next dev` processes
   compiling concurrently corrupted that shared cache several times
   (`ENOENT .next/server/pages/_document.js`, truncated webpack pack
   files, a stale HTML page referencing a `/_next/static/chunks/...`
   bundle that had since been overwritten with a different content hash —
   the last one silently broke React hydration for one page, `/registry`,
   for a long stretch: the DOM showed typed text but the input had zero
   React fiber/props attached, confirmed by direct `page.evaluate`
   inspection with a hand-written Playwright debug script). `rm -rf .next`
   plus a full server restart was the working recovery each time, per this
   task's own briefed guidance for OneDrive-related `.next` corruption —
   done twice before learning port 3001 was the user's own server (not
   safe to keep doing casually; the final clean run did not need it).
3. **Fixed by the spec, not the app.** Every actual production-code path
   this task touched — `src/core/admin`, the two new API routes, the
   three new pages — worked correctly every time it was reachable. All
   fixes that made the gate reliable were in `test/e2e/admin.spec.ts`
   itself: resilient navigation retries for transient non-200s, retrying
   the whole request-link→fetch-link cycle together (the dev-link-store is
   a per-email FIFO queue — retrying only the GET after a POST that
   silently succeeded could starve it), never retrying an already-consumed
   single-use magic-link token, and `.fill()` + `waitForLoadState`
   ("networkidle") instead of `.pressSequentially()` for the registry
   search box once direct backend checks (`fetch` a session cookie, hit
   `/api/registry/search` directly) proved the API itself was never the
   problem.
4. **Once the shared tree quieted down** (all other agents finished and
   committed, confirmed by the orchestrator), a clean run of the exact
   same split-step recipe passed all 4 tests on the first attempt, and the
   determination + a1-letters gate passed all 13 tests on the first
   attempt too — no further spec changes needed. This corroborates that
   the flakiness was environmental contention, not a defect in this task's
   code or its test.
