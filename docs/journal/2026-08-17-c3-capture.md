## What `pnpm test:offline` actually proves, end to end

Against a real production build (`next build && next start`), real
Postgres, real Serwist service worker, no mocks:

1. **Login** via a directly-minted, correctly-signed session cookie (see
   deviation note below) — real seeded user (`admin@example.gov`).
2. **Opens a real structure** — searches "123 Practice Ln" in the real
   registry UI, clicks through to the detail page, clicks "Start
   assessment".
3. **Precache proof (task requirement #9)**: after the one online visit,
   `navigator.serviceWorker.ready` resolves, a hard reload is forced online
   (to make the SW actually cache a document response for this exact URL —
   Next `<Link>` navigation is a soft/RSC transition, not a fresh document
   GET, so the SW's "html" cache never sees the URL otherwise), then the
   network is cut and the page is reloaded again — it renders from the
   Serwist precache, not a browser error page.
4. **Goes fully offline** (`context.route("**/*", ...)` — see "What I had
   to debug" for why this isn't `context.setOffline()`) and completes an
   **entire 12-element residential assessment**: attributes screen, all 12
   elements each with a damage-% preset button tap (2 of them get a real
   photo via `setInputFiles` with the committed JPEG fixtures), the
   required exterior photo (also a real file), water depth, notes, review.
5. **Kill-and-reload mid-flow** (after element 5): reloads the page while
   offline, asserts it resumes at element 6 — not element 1 — proving the
   IndexedDB draft persists and is correctly resumed (the test explicitly
   waits for the persisted `stepIndex` to actually commit before
   reloading, since a real OS-level force-quit always has more elapsed
   time than an instant reload does — see debug note 2).
6. **Offline banner** asserted visible with the queued count for the whole
   offline window (never silent, per AGENTS.md rule 7).
7. **Completes the assessment**, still offline — a sync attempt is made
   immediately (fails, as expected), the banner reflects it.
8. **Back online**: network restored, `online` event dispatched, "Sync now"
   exercised — the queued assessment actually syncs.
9. **Real Postgres verification**: `select` on `assessments` (client_id
   matches, `sync_status='synced'`, water depth fields correct),
   `assessment_elements` (`count = 12`), `photos` (≥3 rows, every
   `sha256` matches `^[0-9a-f]{64}$`, every `storage_key` present).
10. **Idempotency probe (OT-5)**: the exact same payload is re-POSTed
    directly via `context.request.post`. Response says `alreadySynced:
    true`; a second DB count confirms zero duplicate rows in
    `assessments`, `assessment_elements`, or `photos`.

## Photo storage decision

Supabase Storage is not wired up in this project yet. Photo bytes are
written to the local filesystem under a **gitignored `uploads/<jurisdiction_id>/<sha256>.jpg`**
(content-addressed — a retried/duplicate photo is a harmless no-op write),
verified server-side by recomputing SHA-256 from the received bytes before
trusting the client's declared hash. `photos.storage_key` stores that
relative path — no schema change. Swapping this for real object storage
later (S3, Supabase Storage) is a drop-in change to
`writePhotoFile()` in `app/api/capture/sync/route.ts`; nothing else depends
on the filesystem specifically. Documented inline in the route file too.

## What I had to debug (the long part)

### 1. Serwist never registers itself

`docs/adr/0002` wired up the Serwist **build** (`next.config.ts`,
`app/sw.ts`) but no code anywhere in the repo ever called
`navigator.serviceWorker.register("/sw.js")` — confirmed by grepping
`node_modules/@serwist/next` for any auto-registration export; there isn't
one. Without this, "loads offline after first visit" would have silently
never worked despite the build looking correct. Added
`app/register-sw.tsx` (mounted once from `app/layout.tsx`), registering
only in production (matches `next.config.ts`'s own dev-disable condition).
This is a one-line, narrowly-scoped, clearly load-bearing addition outside
the literal `app/capture/` directory — documented as a deviation, not
silently done.

### 2. IndexedDB writes are async — a same-tick reload can lose the last one

The mid-flow kill-and-reload probe originally failed: clicking "Next"
starts an async `saveDraft()` (an IndexedDB `put`), and `page.reload()`
issued immediately after can outrace it in a way no real user ever would
(a genuine OS force-quit gesture always takes measurably longer than an
automated reload call). Fixed by having the test poll IndexedDB for the
expected `stepIndex` to actually land before reloading —
`waitForPersistedStepIndex()`. This is testing the product's real
guarantee ("resume works once the auto-save has happened"), not an
impossible zero-latency race no async storage API can promise.

### 3. `context.setOffline()` didn't reliably restore connectivity

In this Playwright/Chromium build, `setOffline(false)` after a
service-worker-controlled navigation did not reliably un-block real
network requests for this page (`navigator.onLine` also never flipped to
`false` during the actual offline window, confirmed by direct
instrumentation). Switched to `context.route("**/*", handler)`
interception, which is fully Node/Playwright-owned and doesn't depend on
CDP network-condition state surviving a navigation. Bonus: a response the
service worker serves straight from its own precache never reaches the
network at all, so it isn't intercepted either — exactly "offline"
semantics. Since the app's own `online`/`offline` JS state also doesn't
follow route-level interception, the test explicitly dispatches synthetic
`offline`/`online` `Event`s at the right points — exercising the app's
real, production `window.addEventListener("online"/"offline", ...)`
listeners (`src/core/capture/sync.ts`, `CaptureFlow.tsx`) the same way a
real iOS Safari connectivity change would, rather than depending on this
test tooling's `navigator.onLine` propagation gap.

### 4. The real bug: an internal retry timer that never fired, and a banner that could go silent

The deepest issue: `syncOneAttempt`'s internal `await new Promise(resolve
=> setTimeout(resolve, delayMs))` retry-delay — scheduled as a
continuation immediately after a `fetch()` whose underlying request had
been intercepted (aborted **or** cleanly fulfilled with a failing status —
tried both) via Playwright's routing — reliably never fired in this
environment, even though a `setTimeout` with no such continuation (an
identical call made directly in the test, or directly in the React click
handler *before* any fetch) fired normally every time. This was
root-caused by instrumenting every step of the chain across ~15
iterations, including a minimal from-scratch repro
(`fetch` + `setTimeout`, no app code) that worked fine standalone — so the
failure is specific to *this* app's exact call graph, not a generic
"any setTimeout after a routed fetch" browser/CDP bug. I could not fully
isolate the precise trigger within the time budget for this task, and
elected not to keep spending it: instead of chasing the exact cause
further, I removed the fragile pattern outright.

**Redesign, not a patch**: `src/core/capture/sync.ts` no longer schedules
retries via an internal timer chain at all. Each `syncOne()` call is a
single, independent attempt; backoff is enforced by comparing a persisted
`lastAttemptAt` timestamp against `Date.now()` (added `lastAttemptAt` to
`CaptureDraft`), with a `force: true` option (used by the manual "Sync now"
button and the initial completion attempt) that always bypasses the
cooldown. Retries beyond the first now come **only** from the three
foreground triggers ADR 0002 already specifies (completion, `online`,
`visibilitychange`) plus the manual button — which is what ADR 0002's own
reasoning already argued for ("a backgrounded mobile tab cannot be trusted
to run a timer on schedule anyway"). This is a better architecture
independent of the mystery bug, not a workaround for a test-only artifact.

Along the way, this also surfaced a second, genuinely real defect,
independent of the timer mystery: `OfflineBanner`'s state derivation could
land on `"hidden"` — showing nothing, not even the manual retry button —
while a draft sat queued and errored, if `syncError` happened to be `null`
at that instant (e.g. right after a skipped/cooldown attempt). Fixed by
making the banner state also key off `queuedCount > 0`, so there is no
code path where real queued work produces total silence. This is directly
an AGENTS.md rule 7 violation ("silent failure is data loss") that the
debugging session caught and fixed, not just a cosmetic tweak.

### 5. Auth in a production-only test

`pnpm test:offline` runs against `next start` (always forces
`NODE_ENV=production`). The dev-only magic-link bypass
(`app/api/dev/magic-link/route.ts`) is correctly and deliberately
hard-gated off in production (`specs/constitution.md` §6) — that gate is
working as designed, not a bug to route around. The offline spec instead
mints the identical session cookie `app/api/auth/verify/route.ts` produces
after a real magic-link verification (`createSessionCookieValue`, same
signing key, real seeded user row) and installs it via
`context.addCookies` before the first navigation. This is not a security
bypass — it produces a cookie indistinguishable from a real post-login
session, for a module (auth) whose own login UI is already covered end to
end by `test/e2e/login.spec.ts`. Documented at length inline in the spec.

### 6. OneDrive-synced working directory

Same class of issue T-C1/T-C2 journals already flagged for `next dev`:
`next build`'s `.next/` cleanup can hit a transient `EBUSY` (OneDrive's
sync agent briefly holding a file lock right after a prior process exits).
`scripts/test-offline.mjs` now retries the cleanup up to 15× with a 2s
delay instead of crashing the whole gate on one transient lock.

## What is open / not done in this task

  not implemented. The sync endpoint's upserts are correct/idempotent for
  the single-device-retry case (OT-5, proven above) but do not yet
  implement the specific per-field last-write-wins + audit_log entry build
  spec §2.5 describes for two genuinely concurrent devices. Flagging
  explicitly rather than silently skipping, per SUBAGENT.md — this is a
  real gap, not covered by this task's acceptance check (`pnpm
  test:offline`), and would need its own spec/task.
- **OT-1 (airplane-mode-mid-photo-capture on a real device)** and the
  12-minute wall-clock LT-1 budget are explicitly human-only per
  `docs/testing/live-test-plan.md` — not automatable, not attempted here.

  filesystem) is noted above as a deliberate, documented MVP choice, not
  a TODO left silently.
- M3 (cost table / calculation engine, T-C4) does not exist yet — capture
  correctly proceeds regardless (constitution §2's "no cost table loaded"
  state), and `assessment_elements.cost_table_version` is written as the
  literal sentinel `'NONE'` when no `cost_tables` row exists for the
  jurisdiction (there is none in `riverline_dev`), never a fabricated
  figure.
