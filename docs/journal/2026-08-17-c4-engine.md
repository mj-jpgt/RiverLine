## Rounding approach (the part with real correctness risk)

The ratio's 4dp half-up rounding never divides two floats and rounds the
float result. `ratioBasisPoints(totalRepairCost, marketValueUsed)`:

1. Converts both amounts to exact integer **cents** via
   `BigInt(Math.round(x * 100))` — safe because every currency amount the
   engine sees carries at most 2 decimal places (`numeric(12,2)` in
   `schema/core.sql`), and currency-scale floating-point error (~1e-10
   relative) is many orders of magnitude smaller than half a cent for any
   real repair cost or market value.
2. `numerator = totalCents * 10000n`, `quotient = numerator / marketCents`
   (BigInt integer division, truncates toward 0), `remainder = numerator %
   marketCents`.
3. Half-up: `remainder * 2n >= marketCents` rounds the quotient up by one.
   All quantities are non-negative here, so "half-up" and "round half away
   from zero" coincide.

This is exact integer arithmetic end to end — no float division ever
touches the boundary decision. Verified directly:

- G4: `39250 / 80000 = 0.490625` exactly → basis points `4906.25` →
  remainder `2,000,000` of `8,000,000` (< half) → **0.4906**. ✓
- G5: `64000 / 140000 = 0.457142857...` → basis points quotient `4571`,
  remainder `6,000,000` of `14,000,000` (< half) → **0.4571**. ✓
- Self-authored tie proving this is genuinely half-**up**, not
  round-half-even: `12345 / 100000 = 0.12345` exactly, a true 5th-decimal
  tie → **0.1235** (round-half-even would give `0.1234` since 4 is even —
  the test asserts it does NOT do that).
- `0.44995 / 1 -> 0.4500` (ties up onto the BORDERLINE lower boundary,
  inclusive per the README) and `39250/200000 = 0.19625 -> 0.1963` (used
  live in `persist.test.ts`'s real-Postgres case) both verified exact.
- Threshold classification (`NOT_SD`/`BORDERLINE`/`SD`) compares the
  integer basis-points value against `4500n`/`5500n` directly — never
  re-derives the boundary from the divided-back float `ratio` number, so a
  boundary comparison can never be affected by float repr error either.

## What I had to fix along the way

- **A stray global TEST cost table row in `riverline_test`.** An earlier
  draft of `persist.test.ts` seeded the TEST cost table as a **global**
  row (`jurisdiction_id = null`), which made "no cost table loaded" occur
  for *no* jurisdiction in the shared `riverline_test` database — the
  `no_cost_table` test kept returning `ok`. Fixed by scoping the seeded
  test row to the specific test jurisdiction created in `beforeAll`
  instead. The stray global row from the earlier buggy run was manually
  deleted from `riverline_test` once diagnosed (`delete from cost_tables
  where jurisdiction_id is null and version = 'TEST-FIXTURE-v0'`) so it
  doesn't silently mask the same bug for a future test file.
- **`noUncheckedIndexedAccess` + CSS module typing.** `global.d.ts` types
  `*.module.css` imports as `{ readonly [className: string]: string }`.
  Under `noUncheckedIndexedAccess`, even a literal `styles.foo` dot-access
  widens to `string | undefined` because it resolves through an index
  signature. Building a `Record<ThresholdResult, string>` of class names
  directly hit this; switched to a small `statusClass()` function with an
  explicit `as string` cast at each arm, documented inline — no prior
  pattern in the codebase to follow here, so I picked the smallest,
  clearly-commented fix rather than touching `global.d.ts` (out of scope).
- **Next.js dev-tools overlay button collides with `getByRole("button", {
  name: "Next" })`.** Under `pnpm dev` (unlike the production build
  `offline-capture.spec.ts` runs against), Next renders a dev-tools FAB
  whose accessible name is "Open Next.js Dev Tools" — a loose
  `name: "Next"` query matches both it and the real capture-flow "Next"
  button (Playwright substring-matches accessible names by default),
  producing a strict-mode violation. `test/e2e/calculation.spec.ts` uses
  `{ name: "Next", exact: true }` for every "Next" button click.
- **Duplicated "← Back to structure" link** — the blocked-state components
  (`NoCostTableState`, `NoValueState`, `StructureIncompleteState`) each
  briefly rendered their own back-link in addition to the shared
  `PageHeader`'s; Playwright's strict-mode locator caught the duplicate
  immediately. Removed the redundant one from each panel.
- Ambiguous `id` column in a couple of `persist.test.ts`'s own verification
  queries (`calculations c join assessments a`) — qualified as `c.id`.
