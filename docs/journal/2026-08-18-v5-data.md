## Task 1 — dev-db hygiene

### What was actually wrong

The user's read was correct. `riverline_dev` had 37 users; 34 matched
`a2-e2e-%`, `a4-e2e-%`, or `debug-ocr-%` (the exact patterns this project's own
e2e/debug harnesses use — verified by reading `test/e2e/a2-dashboard.spec.ts`'s
own `OFFICIAL_EMAIL` convention before writing the cleaner). Those 34 users
were not loose rows — they each belonged to one of 27 disposable jurisdictions
("A2 E2E Jurisdiction `<ts>-<rand>`", "A4 E2E Jurisdiction `<ts>-<rand>`",
"Debug OCR `<ts>`") that e2e/debug runs create fresh every run and never clean
up. Before deleting anything, I queried the real database directly to confirm
the shape of the problem rather than assume it:

- Every one of the 27 non-"Demo City" jurisdictions had users that were
  **100% pattern-matching** — zero mixed jurisdictions (verified with a direct
  join query).
- 80 of the 3,901 `structures` rows (3,821 are the real Hamilton County
  parcels) belonged to those 27 jurisdictions.
- 68 of the 136 `assessments` rows belonged to them; the other 68 were real,
  repeated manual QA runs by the 3 seeded demo users
  (`admin@example.gov`/`assessor@example.gov`) against the practice structure
  (`123 Practice Ln`, parcel `DEMO-PRACTICE-001`) — legitimate per build spec
  §6.7's "built-in demo structure... so training never touches real records,"
  not pollution, and never touched.

### Design decision: jurisdiction-level cascade, not just user-referential deletes

The task brief's literal wording was "users matching patterns AND every row
that references them." A purely user-referential delete
(`assessments.assessor_user_id`, `determinations.adopted_by_user_id`, etc.)
would have stranded every structure those test runs created — structures
carry no user reference at all, only `jurisdiction_id` — as permanent
orphaned pollution, which would not have fixed the actual symptom (the
dashboard showing fake structures). Since the pattern-match-to-jurisdiction
correspondence was verified 1:1, `computeTargets()` in
`scripts/ops/clean-dev-db.mjs` targets whole jurisdictions where: (a) at
least one user matches a pollution pattern, (b) **every** user in that
jurisdiction matches (one real/mixed user excludes the whole jurisdiction,
unconditionally), (c) the jurisdiction is not named "Demo City", and (d) it
holds no `DEMO-PRACTICE%`-parcel structure. Two independent safety checks
run on the computed result itself (not the query) before any DELETE: the
three protected demo emails must not appear in the target user set, and
"Demo City" must not appear in the target jurisdiction set. Full reasoning
is in the script's own header comment.

### Trigger handling

`calculations` (insert-only) and `audit_log` (append-only) and
`determinations` (no-DELETE) are each protected by a named Postgres trigger
in `schema/core.sql`. `session_replication_role = replica` (the forbidden
hammer) was not used. Instead, the cleanup transaction disables exactly the
three named triggers (`calculations_immutable`, `audit_log_append_only`,
`determinations_no_delete`, plus `determinations_audit` to avoid the
cleanup's own housekeeping UPDATE generating a fresh audit row) via
`ALTER TABLE ... DISABLE TRIGGER <name>`, only for the duration of the one
transaction, and re-enables them before COMMIT. This is transactional DDL in
Postgres — a rollback undoes it along with everything else. Verified this
actually works (not just compiles): after `runCleanup`, a fresh test proves
a brand-new `calculations` row still cannot be `DELETE`d — the trigger is
provably back (`test/unit/ops/clean-dev-db.test.ts`, "re-enables every
trigger afterward").

Two circular/self FKs had to be broken before deletion could proceed:
`determinations.letter_id` <-> `letters.determination_id` (nulled `letter_id`
first), and `estimates.supersedes_estimate_id` (self-referencing version
chain, nulled first).

### Safety rails, all enforced in code (`assertSafeDatabaseName`)

- Refuses any database name other than exactly `riverline_dev` unless
  `--db-override=<name>` is passed.
- The override itself refuses: any `*_test`-suffixed name or literally
  `riverline_test` (test harnesses own those, not this script); any name
  containing "prod"; any name that doesn't start with `riverline_dev` (so an
  override can only ever target an actual clone, never an arbitrary
  database).
- No deletion without `--yes` — without it, prints the preview count table
  and exits, having touched nothing.
- The whole delete is one transaction.

### Filesystem (uploads/)

`cleanJurisdictionUploads` removed `uploads/<jurisdictionId>/` for each
target jurisdiction (photos + estimates share that path). Separately,
`cleanOrphanedUploads` found and removed directories under `uploads/` and
`uploads/letters/` with **no corresponding jurisdiction row at all** —
pre-existing filesystem debris from jurisdictions that had already been
deleted from the database by some earlier process, before this script ever
ran (confirmed: the `letters` table had zero rows in `riverline_dev` at the
start of this task, yet `uploads/letters/` had 12 subdirectories on disk).
These are unambiguously safe to remove (no live FK can reference an id with
no jurisdiction row) and are counted/logged as a distinct category, never
conflated with the jurisdiction-targeted cleanup. Total removed across both
categories: 6 orphaned directories in the real run against `riverline_dev`
(29 in the clone-test run, because the clone-test run's filesystem side
effects were **not isolated from the real `uploads/` folder** — see note
below — so most of what the real run found was already gone).

**One honest caveat, discovered while running this, not anticipated in
advance:** `uploads/` is a single directory shared by whatever database
`DATABASE_URL` happens to point at on this one dev machine — there is no
per-database uploads root. Running the cleaner with `--db-override` against
a DB clone still performs real filesystem deletes, because the same
jurisdiction UUIDs are identical between the clone and the real
`riverline_dev` (it's a byte-for-byte `pg_dump`/restore). In this case that
was harmless and in fact correct (the clone-test run did the real,
necessary filesystem cleanup a step early; the later real-DB run found
those directories already gone and reported 0 removed there), but it means
"test on a copy" for this script is DB-transaction-safe, not
filesystem-safe. Noted here rather than silently glossed over.

### Pollution reappeared mid-session — twice, for two different reasons

Re-running the preview later in the session showed 3 new e2e jurisdictions
had already reappeared, created minutes earlier by other agents' concurrently
running e2e suites. I deliberately left those alone at the time — a
jurisdiction could belong to an in-flight concurrent agent's test run, and
deleting it mid-test would break that agent's suite, not just tidy the
database.

Separately, and worth stating plainly rather than glossing over: getting
`test/e2e/a2-dashboard.spec.ts` to a clean passing run (Task 4) required many
repeated manual `playwright test` invocations against `riverline_dev` itself
(the spec's own `admin = new pg.Client({ connectionString:
process.env.DATABASE_URL })` seeds directly into whatever `DATABASE_URL`
points at — `riverline_dev` in my shell — not `riverline_test`; that's the
existing spec's own design, unrelated to this task, but my repeated runs of
it during troubleshooting compounded the exact problem Task 1 exists to fix).
By the end of Task 4, a fresh 24-jurisdiction/26-user batch had accumulated,
entirely from my own now-finished test runs (confirmed no e2e suite was
concurrently in flight before deleting). Ran `pnpm db:clean-dev --yes` one
final time as part of finishing this work: 24 jurisdictions / 26 users / 105
structures / 85 assessments / 80 calculations / 40 determinations / 4
estimates / 44 audit_log / 46 login_tokens removed. Final verified state of
`riverline_dev`: exactly 1 jurisdiction ("Demo City"), the 3 seeded demo
users, 3,821 real Hamilton County parcels (including the practice
structure), 75 assessments (all on the practice structure — up from 68 at
the start of this task, from ongoing legitimate manual QA by other agents/the
user during the session), 0 calculations/determinations/estimates (all were
test-generated).

The general lesson, not just a one-time fix: the script (`pnpm db:clean-dev`)
is meant to be re-run periodically (e.g. post-merge, when no e2e suite is
known to be running), not treated as a single cure — and any future e2e
work against `test/e2e/a2-dashboard.spec.ts` (or its sibling specs) run
manually outside CI will keep reintroducing this exact pollution, by that
spec's own design, until/unless a future task points it at `riverline_test`
instead.

## Task 2 — data-flows architecture doc

`docs/architecture/data-flows.md`. One paragraph of essence: today, every
byte RiverLine holds is scoped to exactly one jurisdiction via Postgres RLS,
and the only things that leave the system are files a human explicitly
downloads (a letter PDF, an SDE export, a records-request ZIP) — there is no
live integration with FEMA, a county system, or any shared "rescue service"
datastore, and none is described anywhere in the build spec. The document
maps what's already collected against four institutional consumers (FEMA's
SDE tool — served, with an honest caveat that re-keying-free import was
never independently verified; the jurisdiction's own APRA records duty —
served, structurally complete; ICC/HMGP eligibility flagging — not built,
but everything the flag would need already exists on an adopted SD
determination, verified against two FEMA sources fetched via search since
direct fema.gov fetch returns HTTP 403 to automated tools; PDA aggregation
for emergency management — not built, though the new operational summary
[task 3] is exactly the aggregate shape a PDA packet would want), sketches
the schema-level design question A8 (county roll-up) would raise without
implementing any of it (no new role, no migration), and closes with an
explicit "what not to build now" list. All external facts carry a fetched
citation and retrieval date; nothing about FEMA program rules was written
from memory.

## Task 3 — operational summary (a2-dashboard)

Added `getOperationalSummary(jurisdictionId, userId)` to
`src/modules/a2-dashboard/queries.ts`, reusing the same `LATEST_STATE_CTE`
every other query in that file uses (extended with `total_repair_cost` on
`latest_calc` — additive, doesn't change any existing query's output shape).
Returns: total structures, the existing status/band counts, a NEW
occupancy-x-band cross-break (`residential`/`nonResidential`/
`unknownOccupancy`, each broken down `SD`/`BORDERLINE`/`NOT_SD`/
`noCalculation` — the residential/non-residential split maps onto FEMA's own
Individual Assistance vs. Public Assistance program tracks, named explicitly
in `docs/architecture/data-flows.md` §3), computed repair-cost totals (sum of
`calculations.total_repair_cost`, overall and per band, `null` — never a
fabricated 0 — when no calculation exists in a band), and
`adoptedSdCount`: the count of determinations that are **both** `status =
'adopted'` **and** the calculation's `threshold_result = 'SD'` — deliberately
distinct from "SD band count," because a computed SD is a proposal and an
adopted SD is the official's actual decision of record (AGENTS.md rule 12).
Verified this distinction with a dedicated test case (a draft SD structure
that must NOT count toward `adoptedSdCount`).

Exposed on `/dashboard`: a new "Jurisdiction operational picture" section
(residential damage-category group, non-residential damage-category group,
repair-cost-and-adoption group), same text-forward stat-row treatment as the
existing status overview (no icon cards, no left-border-strip cards, per
`docs/design/components.md` §4.2), plus a labeled
"Operational summary (CSV)" export button
(`app/dashboard/export/operational-summary/route.ts`) alongside the existing
CSV/full-export buttons. Role-gated identically to the other dashboard
routes (`admin`/`official` only; verified an `assessor` gets 403).
