- No local `pg_dump`/`psql` on this machine (verified: `which pg_dump` ->

  `docker-compose.yml` (container name `riverline-db-1`, confirmed via
  `docker ps`) ships matching-version client tools, so both scripts shell
  out via `docker exec riverline-db-1 pg_dump|psql ...` — documented in

- `backup.mjs`: plain-SQL `pg_dump` (`--no-owner --no-privileges`, portable
  to a differently-owned restore target) of `riverline_dev`, written to
  `backups/<ISO-timestamp>.sql` (dir gitignored — real database contents,
  never committed).
- `restore.mjs <file> [--target=name] [--force]`: drops+recreates the
  target database (terminates other backends first so a dangling test
  connection can't block the DROP), then pipes the dump file into `psql`
  inside the container. Refuses `--target=riverline_dev` without `--force`
  — a restore is destructive (DROP+CREATE+reload), not a merge, so silently
  overwriting the real dev database on a typo'd/omitted `--target` would be
  a real data-loss footgun. Default target: `riverline_restore_check`.
- Manually verified both directions work against the real container before
  writing the test: `pnpm db:backup` wrote a real 1.2MB dump of the real
  3,821-row `riverline_dev.structures` table; `pnpm db:restore <file>
  --target=riverline_restore_check_manual` restored it with matching counts
  and the practice structure intact; `pnpm db:restore <file>
  --target=riverline_dev` (no `--force`) correctly refused with exit 1.

**Test**: `test/unit/ops/backup-restore.test.ts` — real `pg_dump` of the
real `riverline_dev`, real restore into a disposable
`riverline_restore_check_test` database (dropped in `afterAll`), verified
against the source database via direct Postgres queries (not against the
dump text):
1. `structures` row count matches exactly (and is asserted `> 0` first —
   proof this is real ingested data, not an empty db).
2. The T-C1 seed's practice structure (`123 Practice Ln` /
   `DEMO-PRACTICE-001`, always present in `riverline_dev`) survives with
   **every column** byte-identical (`toEqual`, not just address/parcel_id —

   counts also round-trip, not just `structures`.

## T-C7 — where the element_code drop was, and the fix

Traced exactly where T-C5's journal (`docs/journal/2026-08-17-c5-determination.md`,
"A real, load-bearing gap this task discovered") said it would be:

- **Client side already had it.** `src/core/capture/types.ts`'s
  `PhotoRecord.elementCode` (`null` = the required exterior shot, an SDE
  element code otherwise) and `src/core/capture/payload.ts`'s
  `SyncPhotoPayload.elementCode` both already carried this end to end from
  IndexedDB into the sync wire payload — nothing to fix there.
- **The drop was the INSERT in `app/api/capture/sync/route.ts`'s photo
  loop.** The `insert into photos (...)` statement (previously: `id,
  assessment_id, jurisdiction_id, storage_key, sha256, captured_at,
  gps_lat, gps_lng`) simply never included `element_code` — the column
  didn't exist in `schema/core.sql`/migration 0001 at all, so there was
  nowhere to put it. `photo.elementCode` was parsed by the zod schema and
  then silently discarded.
- **The fix**: `migrations/0004_photos_element_code.sql` — one additive
  `alter table photos add column element_code text;`, nullable, no
  backfill (orchestrator-approved per `specs/core/tasks.md` T-C7's header;
  `schema/core.sql` itself untouched, matching the 0002/0003 precedent).
  `app/api/capture/sync/route.ts`'s photo insert now includes
  `element_code`, mapping the client's `elementCode: null` (the "this is
  the exterior shot" sentinel) to the literal string `'exterior'` at write
  time — `null` in the `photos` table is reserved exclusively for genuinely
  unknown/legacy rows (anything synced before this migration existed), per
  task instructions ("no backfill guessing").

## A one-time flake this session hit and diagnosed (not a real regression)

The first `pnpm test:unit --run` after applying migration 0004 to
`riverline_test` failed one file (`test/unit/engine/persist.test.ts`) with
`column "element_code" of relation "photos" already exists`. Root cause:
Vitest runs test files in parallel workers, and several files
independently call `applyMigrations()` against `riverline_test`
(`test/unit/db/rls.test.ts`, `test/unit/determination/persist.test.ts`,
`test/unit/engine/persist.test.ts`, this task's own
`test/unit/ops/backup-restore.test.ts`'s use of the same test db
indirectly via `withDatabaseName`). The very first time a brand-new
migration file exists, two workers can race: one applies + records
`0004_photos_element_code.sql` in `schema_migrations` and commits, while a
second worker — already past its own "is this recorded yet?" read, before
the first worker's commit — tries to run the same `ALTER TABLE` again and
hits a real Postgres error (the column now exists) before it can record
its own row. This is a pre-existing structural TOCTOU gap in
`scripts/db/migrate.mjs` shared by every prior migration
(0001/0002/0003 never hit it because by the time any two test files raced
against `riverline_test` in the same `vitest run`, those migrations were
already recorded from a previous session) — not something T-C6/T-C7
introduced, and not something this task's module (`scripts/ops/`,
`migrations/`, `src/core/determination/`, `app/api/capture/`) owns fixing.
Confirmed by re-running the exact same command immediately after: 17/17
files, 114/114 tests passed, with `schema_migrations` now showing all four
migrations recorded (`0001`..`0004`), and every subsequent run in this
session was clean. Flagging honestly rather than silently rerunning until
green without explanation.
