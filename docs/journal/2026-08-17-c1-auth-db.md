# 2026-08-17 — T-C1: Database + M0 auth foundation

## What I did

- **Migrations.** `migrations/0001_core_schema.sql` is a byte-for-byte `cp`
  of `schema/core.sql` (never retyped) — verified with `diff` at creation
  time and enforced going forward by a Vitest test
  (`test/unit/db/migration-drift.test.ts`) that fails on any drift between
  the two files.
  - `migrations/0002_auth_login_tokens.sql` adds `login_tokens` (magic-link
    token storage — hashed token, 15-min expiry, single-use `used_at`).
    This is additive infrastructure for M0 auth, not a change to the frozen
    core schema.
  - `migrations/0003_app_role.sql` creates a `NOLOGIN` Postgres role
    `riverline_app`. **Why this exists, and why it's load-bearing:** the
    local dev/test Postgres user (`DATABASE_URL`, `riverline`) is a
    superuser (the official `postgres` Docker image makes `POSTGRES_USER`
    a superuser). Superusers **always** bypass Row-Level Security,
    regardless of `FORCE ROW LEVEL SECURITY` — that's a hard Postgres rule,
    not a config knob. Without a distinct non-superuser role to switch
    into per request, `schema/core.sql`'s RLS policies would silently never
    apply to any app query, and the whole cross-tenant isolation guarantee
    would be fiction. `src/shared/db/client.ts`'s `withTenant()` does
    `SET LOCAL ROLE riverline_app` (transaction-scoped) before setting
    `app.jurisdiction_id`/`app.user_id`; the superuser connection can
    `SET ROLE` to any role without a password or explicit membership grant.
  - `scripts/db/migrate.mjs` was refactored to export `applyMigrations()`
    (kept the exact same SQL-running/transaction/rollback logic) so the RLS
    test suite and `scripts/db/seed.mjs --test` can stand up `riverline_test`
    against the real logic instead of a duplicate.
  - `scripts/db/ensure-database.mjs` — `CREATE DATABASE riverline_test` if
    it doesn't exist yet (connects via the `postgres` maintenance db).

- **`src/shared/db/`** — `pool.ts` (private, never re-exported — "raw pool
  access is not exported to feature code" per the task spec),
  `client.ts` exporting exactly two functions:
  - `withTenant(jurisdictionId, userId, fn)` — every tenant-scoped query
    goes through this. Opens a transaction, `SET LOCAL ROLE riverline_app`,
    `select set_config('app.jurisdiction_id', $1, true)` and same for
    `app.user_id` (transaction-local, third arg `true`, per the task spec),
    runs `fn`, commits or rolls back.
  - `withSystem(fn)` — a narrow, explicitly-documented escape hatch for the
    one place in this codebase that legitimately has no jurisdiction
    context yet: magic-link issuance/verification in `src/core/auth`, which
    has to look up a user (and therefore their jurisdiction) *by email
    alone*, before any session exists. Runs as the superuser connection
    (bypasses RLS), no `SET ROLE`. This wasn't explicitly anticipated in
    the task brief's two-function description, but is necessary — RLS on
    `users` means a plain `withTenant` call is structurally impossible for
    "who is this email, and what jurisdiction are they in." Documented
    inline as auth-only; flagging it here too so it isn't mistaken for a
    generic bypass.

- **`src/core/auth/`**:
  - `crypto.ts` — `generateOpaqueToken()` (32 random bytes, base64url),
    `hashToken()` (sha256 hex). `node:crypto` only, no new dependency.
  - `session.ts` — stateless signed session cookie (HMAC-SHA256 over a
    JSON payload of `{userId, jurisdictionId, role, email, iat, exp}`),
    12h expiry per build spec §7.1 ("sessions expire at 12 hours").
    `SESSION_SECRET` env var, minimum 32 chars, checked at sign/verify time.
  - `magic-link.ts` — `requestMagicLink(email)`: looks up the email in
    `users` (the allowlist — there is no other allowlist store; users exist
    only via seed/invite, no self-signup route anywhere in this module) via
    `withSystem`; if found, issues a single-use token (15-min expiry,
    hashed at rest in `login_tokens`); always returns the same shape
    whether or not the email is allowlisted, so allowlist membership isn't
    leaked via the response. In dev (`NODE_ENV !== 'production'`) logs the
    link server-side and stashes it for the dev-only retrieval route; in
    production, **throws** rather than pretending to send real email — see
    "Open items" below, `docs/BLOCKERS.md` B4.
    `verifyMagicLink(token)`: hash-matches, checks not-expired/not-used,
    marks used, returns the login payload.
  - `role-guard.ts` — `requireRole(session, allowedRoles)` throws
    `AuthError("UNAUTHENTICATED" | "FORBIDDEN")`.
  - `index.ts` — the sole entry point `app/` imports through (required by
    `eslint-plugin-boundaries`, ADR 0003).
  - `dev-link-store.ts` — dev-only in-memory link store. **Had to store it
    on `globalThis`, not a module-level `Map`** — see "What I had to debug"
    below.

- **`app/` auth routes**: `app/login/page.tsx` + `LoginForm.tsx` (client
  component; states: default, focus-visible, disabled, loading, error,
  success — all token-driven via `docs/design/tokens.css`, no raw hex, no
  Tailwind arbitrary values), `app/api/auth/request-link/route.ts`,
  `app/api/auth/verify/route.ts` (sets the httpOnly/secure-in-prod/SameSite
  session cookie, redirects to `/home`), `app/api/auth/logout/route.ts`,
  `app/api/dev/magic-link/route.ts` (hard-gated to non-production, on top
  of the store's own gate), `app/home/page.tsx` (the generic authenticated
  landing page this task's e2e spec proves against — real module landing
  pages belong to their own tasks).

- **Seed script** — `scripts/db/seed.mjs` (`pnpm db:seed`, or `--test` for
  `riverline_test`): idempotent, real rows. "Demo City" jurisdiction with
  `nfip_cid` and `ordinance_citation` both `NULL` (the honest empty state
  per constitution #2 — never filled in), the practice structure
  "123 Practice Ln" (build spec §6.7 — synthetic training values, clearly
  labeled as such in the script's comments, never used as engine input),
  and `admin@example.gov` / `assessor@example.gov` / `official@example.gov`.

- **Tests**:
  - `test/unit/db/migration-drift.test.ts` — byte-identity check.
  - `src/core/auth/crypto.test.ts`, `src/core/auth/session.test.ts` — pure
    unit tests (token uniqueness/hashing, cookie sign/verify round-trip,
    tamper rejection, expiry rejection).
  - `test/unit/db/rls.test.ts` — the real RLS/immutability proof, against a
    real local Postgres (`riverline_test`, created + migrated in
    `beforeAll` via the same `applyMigrations`/`ensureDatabaseExists` the
    CLI scripts use). Inserts jurisdictions A and B via a superuser/owner
    connection (bypasses RLS by design), then, through `withTenant` (the
    app db client) as tenant A: cannot read tenant B's structures (with and
    without an explicit `WHERE`), cannot read tenant B's users, can read
    its own; UPDATE and DELETE on a `calculations` row both raise
    (immutability trigger); DELETE on a `determinations` row raises
    (no-delete trigger); UPDATE on a `determinations` row writes an
    `audit_log` row with the correct `actor_user_id`. No mocks.
  - `test/e2e/login.spec.ts` — real login through the dev magic-link route:
    empty-submit disabled state, fills email, requests link, fetches the
    real link from the dev-only route, navigates to it, lands on `/home`
    authenticated, logs out, and confirms unauthenticated `/home` redirects
    to `/login`. Runs on both `chromium` and `mobile-safari` projects.

## What I had to debug (real findings, not assumptions)

1. **Superuser bypasses RLS regardless of `FORCE ROW LEVEL SECURITY`.**
   This is the reason migration 0003 and the `SET LOCAL ROLE` step in
   `withTenant` exist at all — without them the RLS suite would have
   passed for the wrong reason (nothing was ever actually being filtered).
   Confirmed by first reasoning through Postgres's own documented
   privilege model, then empirically: the suite fails immediately if
   `withTenant`'s `SET LOCAL ROLE` line is removed (tenant A can suddenly
   read tenant B's rows) — spot-checked this by temporarily commenting it
   out and re-running `test:unit`, then restoring it.
2. **Next.js dev-mode module splitting broke the dev-link in-memory
   store.** The POST `/api/auth/request-link` handler and the GET
   `/api/dev/magic-link` handler are compiled as separate route bundles in
   `next dev`; a plain module-level `Map` in `dev-link-store.ts` was
   re-instantiated per route, so the GET route never saw what the POST
   route wrote — verified directly with `curl` (server log showed
   `[dev-auth] magic link for ...` but the GET route responded
   "No pending magic link for that email"). Fixed by keying the store off
   `globalThis` instead — the one thing genuinely shared across the whole
   Node process regardless of per-route bundling (the same trick commonly
   used for Prisma-client singletons under Next dev/HMR). Re-verified with
   `curl` after the fix: POST then GET round-trips correctly.
3. **Playwright WebKit + `fill()` on `type="email"` + React controlled
   input.** `mobile-safari` project's login e2e test kept the submit
   button `disabled` after `emailInput.fill(...)` even though
   `inputValue()` confirmed the DOM value was set correctly — React's
   `onChange` simply wasn't firing. Root-caused with a throwaway debug
   spec (fill → check DOM value → check button state), confirmed switching
   to `pressSequentially()` (real per-character keydown/input events)
   fixes it on WebKit; updated `login.spec.ts` to use `pressSequentially`
   for the email field with a comment explaining why `fill()` isn't safe
   here for a WebKit target. Also bumped that one `toBeEnabled()`
   assertion's timeout to 15s — flaky specifically under the full 6-worker
   parallel run (CPU contention slowing real WebKit event dispatch), not
   flaky in isolation (verified `--workers=1 --repeat-each=3`, 3/3 green).

## What is open / deviations

- **B4 (new, in `docs/BLOCKERS.md`): no production email transport.**
  `requestMagicLink()` throws a clear error in production rather than
  faking a send — sending real mail needs a chosen provider, credentials,
  and an ADR for the new dependency (AGENTS.md rule 3), none of which
  exist. Dev/test flow (what's actually exercised by the e2e spec) is
  fully real: request → hashed single-use token → dev-only retrieval route
  → verify → session.
- **`withSystem()` escape hatch.** Not explicitly named in the task's
  "export `withTenant`, raw pool not exported" description, but necessary:
  magic-link issuance/verification has no jurisdiction context yet. Scoped
  narrowly to `src/core/auth`, documented in `src/shared/db/client.ts` and
  above. Flagging this as a design decision made under the task, not a
  literal instruction.
- **`migrations/0002` and `0003`** add a token-storage table and a
  Postgres role that aren't part of `schema/core.sql`. `schema/core.sql`
  itself is untouched (verified byte-identical by
  `migration-drift.test.ts`); these are additive, forward-only,
  auth-infrastructure migrations, not changes to the frozen core schema.
  Flagging per AGENTS.md rule 1's "propose a diff... a human approves
  schema changes" — this isn't a diff to the frozen file, but it is new
  schema surface a human should be aware of.
