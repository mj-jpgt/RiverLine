## 1. Duplicates — root cause

Queried `select address, count(*) from structures group by 1 having
count(*) > 1` on both databases. Top result: `0 Walnut St`, 22 rows. Pulled
all 22: **22 distinct `parcel_id` values**, all `prop_class = '640'`
(DLGF exempt-property range — these are small municipal/utility/ROW
parcels with no house number, hence the literal `"0 <street>"` address).
`select jurisdiction_id, parcel_id, count(*) ... having count(*) > 1` on
both databases returned **zero rows** — the schema's `unique
(jurisdiction_id, parcel_id)` constraint holds, ingest has no bug, and every
"duplicate" is a legitimate, distinct real parcel.

**Root cause: the UI, not the data.** `RegistrySearch.tsx`'s result rows
rendered only the address string, `sfhaZone`, and an "occupancy unset"
badge — no parcel number, no property class, no value. Two genuinely
different parcels sharing one situs address were visually indistinguishable
list items.

**Fix:** `src/core/registry/types.ts`/`queries.ts` now select and return
`propClass` and `improvementValue` alongside the existing `parcelId` on both
`searchStructuresByAddress` and `nearestStructures`.
`app/registry/RegistrySearch.tsx` renders `Parcel <id> · Class <code> ·
<value or "No value on file">` under every address, plus an "Unverified
manual entry" badge where applicable (see §4). Nothing was deduplicated —
every legitimate distinct parcel still appears as its own row, now
identifiable. New e2e coverage: `test/e2e/registry-f1.spec.ts` (`F1
registry: duplicate disambiguation`) asserts on `0 Walnut St` directly:
more than one result, every row states a parcel number, no two rows share
one.

## 2. Value fields blank — investigation and before/after counts

The field report's example, 16780 River Rd (parcel `1010010000019000`,
class 300), was queried directly against the live Hamilton County
FeatureServer for that exact `PARCELNO`. The source record itself has
`AVIMPROVE: null`, `sq_ft_res: null`, `sq_ft_comm: null`, `year_built: null`
— and `PROPUSE: "Ind. - Vacant land"` (owned by Indianapolis's Department of
Public Utilities as a water-system trust parcel). **This is not an ingest
defect; the county has no improvement on file for this parcel because
there is no assessed structure there.** AGENTS.md rule 4 forbids inventing a
value here — the honest fix is not to fabricate a number.

To rule out a real mapping bug elsewhere, I cross-checked every cached
source feature against the local dev DB (`AVIMPROVE` vs. `improvement_value`,
and `pickSqFt`'s expected value vs. `sq_ft`) for all 3,840 previously-loaded
rows: **zero mismatches, zero cases where the source had a value the DB
didn't.** `improvement_value`/`sq_ft` mapping in `ingest-parcels.mjs` was
already correct.

**Before/after null counts** (re-ran the existing bbox ingest idempotently
against both DBs to confirm — see `ON CONFLICT ... DO UPDATE`, safe
re-run):
- Local dev, bbox scope (3,841 rows): `improvement_value` null 540 → 540,
  `sq_ft` null 540 → 540 (unchanged — confirms no bug, not a no-op check).
- Full-county ingest results are in §4 below (the null *rate* stayed
  consistent at county scale — see there).

**What I actually changed here:** UI copy only. `formatCurrency`'s
"Not available" became "Not on file" (consistent with every other blank
field on the page); `VALUE_SOURCE_LABELS` rewritten in plain language
without em dashes (user directive) — e.g. `assessed_improvement` now reads
"Assessed improvement value. The county assessor's record, not a market
value. An official confirms the market value used for the determination."
instead of "Assessed improvement value — market value pending, see
official". The real fix for "too many blanks" is enrichment (§3) and
coverage (§4), not a data-mapping change that didn't exist to make.

## 3. Autofill / enrichment

**Design:** suggestions, never silent finals, per the task's hard
constraint. New module `src/core/registry/hamco-source.ts`:
`fetchCountyParcelRecord(parcelId)` does a single `where PARCELNO=$1` REST
call (no geometry, no join) against the same FeatureServer the ingest
script uses — **this is a single-feature attribute lookup, not raster or
spatial-join work**, so it does not violate AGENTS.md's "Geospatial" rule
(preprocessing owns joins/rasters; this reads one row by key, same category
of read `nearestStructures()`'s `ST_Distance` call already makes against a
precomputed column). `buildEnrichmentSuggestions()` compares the fetched
record against the structure's current row and returns a suggestion **only
for fields that are currently NULL** — a field that already has a value is
never even offered a "suggested change," so "never overwrite an existing
user-entered value" is true by construction at the suggestion stage, and
enforced again with a `where column is null` guard on the actual `UPDATE`
in `applyEnrichment()` (defense in depth against a race between the
suggestion being shown and being accepted).

**Provenance:** `structures` has no per-field provenance column and the
frozen schema (rule 1) wasn't touched to add one. Instead, every accepted
field writes an `audit_log` row (`entity_type: 'structure'`, `action:
'enrichment_accepted'`, `before_json`/`after_json` carrying the field name,
old value, new value, and a source label like "County assessor record,
fetched 2026-08-18") — `audit_log` already exists precisely for this kind
of append-only record and needed no migration.

**UI:** `app/registry/[id]/EnrichmentPanel.tsx`, a client component that
auto-checks the county record on mount **only if the structure has a
tracked field currently missing** (improvement value, sq ft, year built,
stories, or occupancy) — this is the "automatic prefill at assessment
start" the task asked for. I deliberately implemented it on the **registry
detail page**, not inside the capture flow: `src/core/capture/` and
`app/api/capture/` are F2's module (explicitly off-limits), and in this
app's real flow the registry detail page is exactly the screen an assessor
lands on immediately before clicking "Start assessment" — so a background
check there, with results already accepted (or not) by the time they click
through, achieves the same effect without crossing the module boundary.
Each suggestion renders as an editable text input (prefilled with the
suggested value, source label underneath) with its own **Accept** button —
nothing saves until that specific field is accepted. A manual "Refresh from
county records" retry button covers the unavailable case. If the county
service is unreachable or times out (6s timeout, `AbortController`), the
panel degrades to "No suggestions... enter values by hand below" with no
error styling — offline-first, never a scary banner.

**Route:** `app/api/registry/[id]/enrich/route.ts` — `GET` (read-only
suggest, never a 5xx for a county outage) and `POST` (accept one or more
fields). Bug found and fixed while building the e2e test for this: Zod v4's
`z.record(z.enum([...]), valueSchema)` requires **every** enum key present
(verified empirically — `z.record(z.enum(["a","b"]), z.number())` rejects
`{a: 1}` with "b: expected number, received undefined"), which meant
accepting a single field always failed with "At least one field is
required." Fixed by switching to `z.partialRecord`, the v4 API for
partial-key records. Confirmed via direct `curl` against a running dev
server before and after.

## 4. Coverage — full county ingest

**Before:** the bbox envelope covered only ~3,821 of the county's 153,883
parcels. A real flooded address outside that envelope had no structure row
at all, which is exactly the report's underlying complaint.

`scripts/preprocess/ingest-parcels.mjs --full` (or `INGEST_MODE=full`) now
supports whole-county ingest: `where=1=1` paging for parcels (no geometry
filter), and paged NFHL zone/panel fetches (verified live 2026-08-18:
4,670 zone features / 89 panel features county-wide vs. the bbox's 146/4 —
the original single-request assumption for NFHL layers doesn't hold at
county scale).

**Two real bugs found and fixed while running the first full-county
attempt, both documented in code comments where fixed:**
1. `ON CONFLICT DO UPDATE command cannot affect row a second time` — the
   live FeatureServer occasionally returns the same `PARCELNO` twice within
   one 1000-row page (hit at offset ~38000). Fixed by de-duplicating each
   upsert batch by `parcel_id` (keeping the last occurrence) before building
   the multi-row `INSERT`.
2. **Point-in-polygon performance at scale.** The existing
   `pointInEsriPolygon` ray-casting test has no cheap reject — at
   county scale (150k parcels × 4,670 zone polygons) this made each
   10-minute foreground run net *less* progress than the last, because
   every re-run redid every earlier page's point-in-polygon work before
   reaching new pages (the per-page fetch cache alone wasn't enough).
   Fixed two ways: (a) added a bounding-box pre-filter (`featureBbox` /
   cached per feature) so a point is only ray-cast against zones whose
   bbox actually contains it, and (b) added a **separate DB-upsert
   checkpoint** (`upsert_checkpoint_<hash-of-DATABASE_URL>.json`, distinct
   from the fetch-page cache) so a re-run resumes DB work from the last
   *committed* page instead of redoing everything from page 0. Together
   these took the run from "no visible progress across two full 10-minute
   windows" to completing the remaining ~90,000 rows in about 12 minutes.

**Final counts, both databases, full county, 2026-08-18:**
| | before | after |
|---|---|---|
| Local dev (`riverline_dev`) | 3,841 | **152,896** |
| Live (Supabase) | 3,821 | **152,876** |

(The gap to 153,883 is parcels with a null `PARCELNO` or `LOCADDRESS` in
the source — the ingest has always skipped those rather than invent a key,
unchanged behavior.) `improvement_value`/`sq_ft` null rates stayed
consistent with the bbox subset (~14%) at full county scale — this
confirms §2's finding: the blanks are the source's own coverage gaps, not
an ingest defect that scaling up would have made worse.

**The honest remainder:** even full-county coverage will never be 100% —
new construction, data lag, or a parcel genuinely outside Hamilton County
can still leave an assessor with nothing to search for. `app/registry/new/`
(new page + `ManualStructureForm.tsx` + `POST /api/registry`) is the
"Structure not found?" path, reachable from the search page's empty state.
Address is the only required field; parcel number is optional (a synthetic
`MANUAL-<id>` is generated when omitted — this prefix can never collide
with a real 16-digit `PARCELNO`). Every hand-created row is flagged via a
fixed sentinel prefix in a new nullable `structures.notes` column
(`migrations/0006_structures_notes.sql` — additive, applied to both DBs;
see "Schema" below for why this needed a migration) and rendered as
"Unverified manual entry" on both the detail page and search result rows.
Submitting a parcel number that collides with an already-ingested real
parcel fails with a clear in-page error (409-style message, not a crash) —
covered by `registry-f1.spec.ts`.

## Schema note (additive migration, not a `core.sql` edit)

`structures.value_source` is a required, fixed 5-value enum with nothing
meaning "hand-entered, no source yet" — every existing member describes a
*valuation methodology* (assessed/appraisal/override), not record
provenance. `structures` also has no free-text column at all (unlike
`assessments.notes` / `determinations.notes`, which already exist for
exactly this purpose). No existing column could honestly carry the
"unverified manual entry" flag, so `migrations/0006_structures_notes.sql`
adds a nullable `notes` text column — following the exact precedent
0002/0003/0004/0005 already set for extending outside the frozen
`schema/core.sql`. Applied to both `riverline_dev` and the live Supabase DB
via `pnpm db:migrate`.

Separately, `createManualStructure()` still had to pick a `value_source`
enum value for a record that has none of the five real meanings. I reused
`'official_override'` ("a human, not an automated feed, is asserting this
record") rather than invent a sixth enum value on the frozen check
constraint. This is a judgment call, not a guess about a fact — flagging it
here in case a human wants a dedicated enum member later; it would be a
one-line additive `CHECK` constraint change if so.
