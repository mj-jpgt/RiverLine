## Deviation: capture flow hides the shell, doesn't slim it

The task allowed "slim or hidden" on the capture flow. I chose **hidden**
entirely, not slimmed, for two reasons: (1) `app/capture/[id]/
_components/OfflineBanner.tsx` already ships its own persistent, full-width
offline/sync banner — a slimmed shell strip would show the *same* real
state (queue count, sync status) twice, in two different visual
treatments, which is confusing rather than helpful; (2)
`docs/agents/SUBAGENT.md`'s field-conditions section is explicit that the
capture flow is "one decision per screen. Large type." on a phone, in
sunlight, with wet gloves — even a slim header row is a second UI system
competing for the same cramped viewport as the actual capture controls.
`test/e2e/shell.spec.ts` test 3 proves the hide is real (all three shell
landmarks asserted absent on `/capture/[id]`) and that it doesn't affect
capture's own UI.

## A real environment problem this task hit (not invented around)

All four concurrent agents share **one working directory**, not isolated
git worktrees as `docs/agents/SUBAGENT.md` states ("You are one of several
agents working in isolated git worktrees") — empirically false in this
session: another agent's `next dev` was already bound to port 3000 against
the same `.next` output directory. Starting a second `next dev` on port
3500 against that same shared `.next` corrupted it for both processes
(`ENOENT: routes-manifest.json`, `Cannot find module './9190.js'`, HTTP 500s
on `/` and `/login`) — the exact class of problem the environment notes'
"delete `.next` and retry" guidance anticipates, but that fix alone doesn't
prevent a second concurrent writer from re-corrupting it. Deleted `.next`
once to un-stick the shared server (self-heals on next request, confirmed
working afterward), then built genuine isolation instead of guessing again:
copied the source tree (excluding `node_modules`/`.next`/`.git`, ~seconds
via `robocopy`) into the agent scratchpad, junctioned `node_modules` to the
real one (`mklink /J`, no copy, no reinstall), and ran my own `next dev -p
3500` there with its **own** `.next`. All verification below that isn't the
final literal root-suite command ran against that isolated server — same
source files (this task's actual changes), same `riverline_dev` Postgres,
zero risk of corrupting or being corrupted by another agent's process.
