# 2026-08-17 — T-C2: M1 structure registry + real parcel ingest

## What I did

- **Ingest — `scripts/preprocess/ingest-parcels.mjs`** (`pnpm ingest:parcels`).
  A plain Node script (tabular REST paging, not raster work — Python/GeoPandas
  stays reserved for future depth-grid work per AGENTS.md "Geospatial"), that:
  - Pages the live Hamilton County parcel FeatureServer
    (`docs/data-contracts/hamilton-county-parcels.md`) with `resultOffset`
    paging (1000/page), a 350ms polite delay between pages, and
    retry-with-exponential-backoff (4 attempts) on transient failures.
  - Bounds the pull to a WGS84 envelope around downtown Noblesville / the
    White River corridor: `-86.03,40.03,-85.99,40.06`. Chosen empirically —
    queried `returnCountOnly` for three candidate envelopes live against the
    service (documented in the script header): 7,260 / **3,842** / 12,284
    parcels. Picked the 3,842 envelope (inside the 1,000–5,000 target) and
    it happens to straddle the river, so the flood-zone join produces real
    zone diversity, not just Zone X.
  - Caches every raw page/layer response under `data/raw/ingest/` (already
    covered by the existing `data/raw/` gitignore rule) — confirmed
    re-runnable fully offline by re-running with the cache present (see
    acceptance output below: second run shows "cached" for every fetch, 0
    network calls, same row counts).
  - Pulls NFHL Layer 28 (Flood Hazard Zones) and Layer 3 (FIRM Panels) for
    the same envelope, filtered to `DFIRM_ID='18057C'`
    (`docs/data-contracts/fema-nfhl.md`) — 146 zone polygons, 4 FIRM panels
    for this bbox, both fetched whole (no paging needed at that size).
  - Does the point-in-polygon assignment **in the script** (preprocessing —
    explicitly allowed by the task; the serving path in
    `src/core/registry` never does this): area-weighted centroid (shoelace
    formula) of each parcel's outer ring, then an even-odd point-in-polygon
    test (summed across all rings, so holes are handled correctly without
    needing to know ring winding) against every fetched zone/panel polygon.
    A parcel whose centroid falls outside every fetched polygon gets
    `sfha_zone`/`firm_panel` left `NULL` — never guessed as "X" or anything
    else.
  - Maps `PROPCLASS` → `occupancy_type` per
    `docs/data-contracts/dlgf-property-classes.md`'s documented ranges:
    `499–599` → `residential`; the rest of the documented DLGF ranges
    (`100–398`, `399/403–498`, `600–899`) → `non_residential`; **codes 400,
    401, 402 (DLGF "commercial" apartment codes) are mapped to `NULL`**, not
    `non_residential` — the contract's own "Gaps and risks" #2 flags that
    whether apartment buildings should route to SDE-residential or
    SDE-non-residential was never checked against the SDE manual, i.e. it's
    an explicitly open, unresolved question, so "never guess" applies to it
    specifically, not just to codes outside every documented range.
  - `assessor_market_value` is always `NULL` (no market-value field exists
    in the source — `hamilton-county-parcels.md` Gaps #1 / `docs/BLOCKERS.md`
    B3). `improvement_value = AVIMPROVE`. `value_source =
    'assessed_improvement'`. `value_as_of_date` derived from `AVTAXYR` as
    `${AVTAXYR}-01-01` (a bare tax year, not a specific date — documented in
    the script as a labeling convention on an already-real number, not a
    fabricated adjustment).
  - `num_floors` parsed per the contract's documented gotcha (arrives as a
    string with a trailing space, e.g. `"1.0 "`) into an integer `stories`.
  - Upserts into `structures` for the "Demo City" jurisdiction (T-C1's seed)
    on the schema's own `unique (jurisdiction_id, parcel_id)` constraint —
    `ON CONFLICT ... DO UPDATE`, with `occupancy_type =
    coalesce(structures.occupancy_type, excluded.occupancy_type)` so a
    re-run never clobbers an assessor's field-entered occupancy correction.
  - **DB connection choice:** a plain `pg.Client` (superuser `DATABASE_URL`),
    the same pattern `scripts/db/seed.mjs` already uses — not
    `withSystem()`/`withTenant()` from `src/shared/db`. This is a batch/ops
    script like `seed.mjs`/`migrate.mjs`, not app request-path code; there's
    exactly one jurisdiction for the whole run (looked up once by name), so
    no per-request tenant scoping is needed, and importing a TypeScript
    module tree from `src/shared` into a plain `.mjs` preprocessing script
    would cross a boundary nothing else in `scripts/` crosses. Documented
    inline in the script header.

- **Registry module — `src/core/registry/`**:
  - `types.ts` — a registry-local `Structure` view (`RegistrySearchResult`,
    `RegistryNearbyResult`, `RegistryStructureDetail`), deliberately
    *not* reusing `src/shared/types.ts`'s `Structure` — that interface
    predates `schema/core.sql` landing and is missing columns this module
    needs (`sq_ft`, `year_built`, `prop_class`), and editing
    `src/shared/types.ts` is outside this task's module directory.
  - `queries.ts` — every function goes through `withTenant()`
    (`src/shared/db`): `searchStructuresByAddress` (ILIKE type-ahead, min 2
    chars, 20-row cap), `nearestStructures` (PostGIS `ST_Distance` on the

    precomputed `geom` column, no request-time spatial join), `getStructureById`,
    `setOccupancyType` (only succeeds while `occupancy_type IS NULL`,
    returns a distinguishable `already_set` vs `not_found` result).
  - `index.ts` — the sole entry point, per `docs/adr/0003`.

- **App routes**:
  - `app/registry/page.tsx` + `RegistrySearch.tsx` (client) — address
    type-ahead (debounced 300ms) and "Use my location" (browser
    Geolocation → `/api/registry/near`). States: idle prompt, loading
    (`role="status"`), error (`role="alert"`), empty ("No structures match
    that address" / "...near your current location"), results list. Route-
    segment `loading.tsx` and `error.tsx` for the server-component session

  - `app/registry/[id]/page.tsx` + `OccupancyEditor.tsx` (client) — parcel

  - `app/api/registry/search/route.ts`, `app/api/registry/near/route.ts`,
    `app/api/registry/[id]/occupancy/route.ts` — all session-guarded via
    `requireRole()` from `@/core/auth` (read routes: all 4 roles; the

  - `app/capture/[id]/page.tsx` — the explicitly-requested stub route: a
    designed placeholder (not an unstyled dead end, not a 404) stating

  - Every page/component uses `docs/design/tokens.css` tokens only — no raw

## What I had to debug

1. **`pg` returns Postgres `date`/`timestamptz` columns as JS `Date`
   objects, not strings**, even though `structures.value_as_of_date` and
   `.created_at` are typed `string` in my TS interfaces (a cast, not a
   runtime guarantee). Rendering `structure.valueAsOfDate` directly in the
   detail page crashed with `Error: Objects are not valid as a React child
   (found: [object Date])` — Next.js silently fell back to client rendering
   with a big flight-payload string embedding the stack trace, which then
   tripped my own `error.tsx` boundary ("This structure could not load
   right now"), making the real cause non-obvious from the browser alone.
   Root-caused by `curl`-ing the RSC payload directly with a real session
   cookie and grepping for `Error:` in it. Fixed with explicit
   `toIsoDate()`/`toIsoTimestamp()` converters in `queries.ts` that check
   `instanceof Date` before formatting — not a `cast and hope` situation.
2. **E2E magic-link races.** `test/e2e/registry.spec.ts`'s two login-using
   tests, run under Playwright's default parallelism, raced against each
   other (and against `login.spec.ts` in the full suite run) because
   `src/core/auth/dev-link-store.ts` (T-C1) holds one pending link **per
   email** on `globalThis` — two concurrent `POST
   /api/auth/request-link` calls for the same email can have the second
   overwrite the first before it's consumed, so the first test's `GET
   /api/dev/magic-link` fetches an already-issued-to-someone-else (or
   about-to-be-superseded) token and lands on `/login?error=invalid_token`.
   Fixed two ways: (a) `test.describe.configure({ mode: "serial" })` inside
   `registry.spec.ts` so its own two login-flows never overlap, and (b)
   using `official@example.gov` instead of `login.spec.ts`'s
   `assessor@example.gov`, so the two spec files never collide with each
   other across the full `pnpm test:e2e` run. Verified by running the full
   suite three times in a row (12/12 green each time) after the fix.
   Not a bug in my code, but a real, load-bearing gap in the shared
   dev-auth test fixture worth flagging for whoever next adds an e2e spec
   with its own login flow.
3. **Cold-`.next`/first-compile flakiness**, same class of thing T-C1's
   journal already documented for WebKit under full-parallel load: a
   from-scratch `pnpm test:e2e` run occasionally raced a not-yet-compiled
   route's first request against a 5s Playwright expect timeout. Not
   something this task's code caused or can fix (it's Next dev-mode
   compile-on-first-request behavior colliding with test parallelism);
   worked around for verification by curling every new route once to warm
   the compile cache before running the suite, exactly as manual dev
   testing already does. Also hit two `EINVAL: invalid argument, readlink`
   crashes from `next dev` — this repo lives inside a  OneDrive-synced
   folder, which does not play well with Next's `.next/` directory when a
   previous dev-server process is killed uncleanly; `rm -rf .next` and a
   clean restart resolved it both times. Flagging as an environment note,
   not a code change.
