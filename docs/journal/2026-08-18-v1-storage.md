# 2026-08-18 — V1: pluggable object storage (local + Supabase drivers)

## What I did

Unblocked the Vercel deploy path per `docs/deploy/vercel-notes.md`: built
`src/shared/storage/` — a minimal interface (`put`/`get`/`exists`) with two
drivers selected by `STORAGE_DRIVER` — and swapped every filesystem call
site onto it, byte-identical semantics for the local driver.

- **`src/shared/storage/types.ts`** — the `StorageDriver` interface:
  `put(key, bytes, contentType)`, `get(key) -> {bytes, contentType}`,
  `exists(key)`.
- **`src/shared/storage/local.ts`** — writes/reads under
  `process.cwd()/uploads/<key>`, the exact pre-existing path. Content-type
  is derived from the key's extension (`.jpg`→`image/jpeg`,
  `.html`→`text/html`) since the filesystem never stored it — correct for
  every key this app has ever produced. `rootDir` is an optional
  constructor param (defaults to the real path) so tests can point it at a
  real temp dir without touching production behavior.
- **`src/shared/storage/supabase.ts`** — `@supabase/supabase-js`
  (already installed, no new dependency). `put()` uses `upsert: true`
  (upload() defaults to `false`, which would 409 on a retried
  content-addressed write the local driver always allowed). `get()` reads
  `Blob.type`/`Blob.arrayBuffer()` from `download()`. Method signatures
  read directly from the installed package source
  (`node_modules/.pnpm/@supabase+storage-js@2.112.3/...`), not recalled —
  see `docs/adr/0008-object-storage.md` "Sources."
- **`src/shared/storage/index.ts`** — `getStorageDriver()`, selecting by
  `STORAGE_DRIVER` (`local` default / `supabase`), re-read on every call
  (no caching), so a test can flip drivers without a reset hook.
- **Six call sites swapped** (the task named four; the actual write/read
  code for two of those four lives one file down — `src/modules/a4-estimates/actions.ts`
  for "the upload route," `src/modules/a1-letters/queries.ts` for "letter
  HTML" reads):
  - `app/api/capture/sync/route.ts` — photo writes
  - `app/api/photos/[id]/route.ts` — photo serving
  - `src/modules/a4-estimates/actions.ts` — estimate page writes
  - `app/api/estimates/document/[estimateId]/image/[pageIndex]/route.ts` — estimate page serving
  - `src/modules/a1-letters/actions.ts` — letter HTML writes
  - `src/modules/a1-letters/queries.ts` — letter HTML reads
  All six diffs are storage-call swaps only — no restructuring, no
  behavior change to auth, RLS/`withTenant` scoping, hash verification, or
  key formats.
- **`docs/adr/0008-object-storage.md`** — interface, driver selection, why
  serving stays an authenticated proxy (not a public/signed bucket URL —
  documented as explicit future work), Vercel implication, local dev
  unchanged.
- **`.env.example`** — additive: `STORAGE_DRIVER` (default `local`),
  `STORAGE_BUCKET`.
- **`docs/deploy/vercel-notes.md`** — storage section flipped from
  "blocker" to "resolved."
- **Tests** (`test/unit/storage/`): local driver (real temp dir, 9 tests),
  driver selection (7 tests, including the unknown-driver-value and
  missing-supabase-env-var cases), and a real (no-mock) Supabase contract
  test that skips visibly when credentials aren't in env.

## A real bug the live contract test caught that a mock never would have

The orchestrator provisioned live Supabase credentials mid-task
(`.env.supabase`, gitignored). Ran the contract test for real against the
live project (created the `uploads` bucket, private, via the service
client since it didn't exist yet) instead of leaving it skipped. First run:
3/4 passed, `exists()` failed with a real `StorageApiError: Bad Request
(400)` for a genuinely-missing nested key. Root cause, found by reading
the installed SDK source's own `exists()` implementation
(`StorageFileApi.ts:987-1025`): unlike every other method, `exists()`'s
return type is `data: boolean` in **both** the success and error branches,
specifically because the real HEAD-request API surfaces "not found" as
either a 404 or (verified against the live API, not just the SDK's own
comment) a 400 for some missing-nested-path cases. My driver's original
`exists()` treated any non-null `error` as fatal and threw — wrong for
this one method. Fixed in `src/shared/storage/supabase.ts` to trust `data`
unconditionally, matching the SDK's own contract. Re-ran: all 4/4 pass
against the live bucket. Cleaned up every probe object afterward
(`client.storage.from(bucket).remove([...])` directly — the interface
itself has no delete, by design, see the ADR).
