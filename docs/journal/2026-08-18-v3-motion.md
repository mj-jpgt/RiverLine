**Calm loading/syncing indicators.** No spinner component existed anywhere

`EstimatesSearch.tsx`), and both sync/offline banners
(`OfflineBanner.tsx`'s "syncing" state, `SyncStatusIndicator.tsx`'s

**iOS Safari `:active` fix (real finding, not speculative) —
`src/shared/ui/EnableTouchActiveStates.tsx`.** WebKit does not apply
`:active` to plain tappable elements at all under touch until some
`touchstart` listener exists anywhere on the page. Verified this for real,
not from memory: `test/e2e/motion.spec.ts`'s pressed-state check passed on
`<button>` elements under Playwright's `mobile-safari` project but
initially failed specifically on `<a>` elements (`.resultLink`) — the
exact signature of this documented WebKit quirk. Added a one-line no-op
`touchstart` listener at the true document root (`app/layout.tsx`, mirrors
the existing `RegisterServiceWorker` pattern) — the standard, documented
fix, zero new dependencies. Without it, every pressed-state rule this pass
wrote would have silently not fired on the primary field device.

## What I found and fixed that wasn't "polish"

**`app/globals.css`'s CSS comment corrupted the entire global
reduced-motion rule.** My first draft's comment read `app/**/*.module.css`
— the substring `**/*` contains a literal `*/`, which closes a CSS comment
immediately. Everything after that point (several more sentences) became
raw, invalid CSS text spliced into the next real rule, corrupting the
`@media (prefers-reduced-motion: reduce)` block's selector into garbage
(`:is(*.module.css and src/shared/ui/**/*.module.css during this pass...) *`
— confirmed by fetching the actual built CSS from a running server and
finding this exact mangled text). The practical effect: the global
reduced-motion safety net silently did nothing — `prefers-reduced-motion:
reduce` would not have disabled a single animation in production, the
opposite of what it exists to do. Caught by `test/e2e/motion.spec.ts`'s
reduced-motion test failing with a real (not near-zero) transition
duration, root-caused by diffing the served CSS against source, fixed by
rewording the comment to avoid the `**/*` glob pattern. This is exactly
the kind of thing "a screenshot is not proof" (`docs/agents/SUBAGENT.md`)
exists to catch — this bug was visually invisible; only a live computed-
style assertion under `page.emulateMedia({ reducedMotion: "reduce" })`
surfaced it.

## A near-incident during this pass — full disclosure, corrected

Following this task's environment instructions ("run your own server on
port 4300 for testing"), I first started a second `next dev` process
directly from the main Riverline checkout, on port 4300 — sharing the
**same `.next` build directory** any other Riverline dev process on this
machine also uses. That process's own log showed real `ENOENT` errors on
`.next/cache/webpack/...pack.gz` and a `TypeError: Cannot read properties
of undefined (reading 'call')` — genuine evidence that running a second
`next dev` against a shared `.next` is a real collision risk, exactly as
`docs/agents/SUBAGENT.md`'s "corrected 2026-08-17 after W1 hit a real
`.next` collision" note describes.

At that point port 3000 started returning 500 for page routes, and I
initially assumed — based on this task's own brief stating "the user's dev
server runs on port 3000" — that I had broken it, and spent real effort
trying to recover it (deleting `.next` once, per this environment's own
documented `.next` EINVAL recovery step; waiting; re-checking). **On
closer inspection this assumption was wrong.** Process-level inspection
(`Get-CimInstance Win32_Process`) shows the process actually bound to port
3000 runs `next start` from `C:\Temp\telo-web` — an entirely different
project, not this repository, with its own separate `node_modules` and
`.next`. It could not have been affected by anything I did to
`C:\Users\mobar\OneDrive\Riverline\.next`, and by the time I checked again
it was serving real content (200, confirmed `telo-web`-branded HTML) —
whatever its earlier 500 was, it was not caused by me and had nothing to
do with Riverline. **I did not break the user's Riverline dev server; I
misdiagnosed an unrelated process's transient state as my own fault and
should have checked what was actually listening on port 3000 before
concluding that.** The one confirmed, real risk from this pass is the
shared-`.next` collision itself — a genuine `next dev`-vs-`next dev`
problem, independent of which port anything ended up on — and I mention
it as a finding for future agents in this environment: a second `next dev`
against the same checkout's `.next`, even briefly, produces real,
user-visible corruption in the dev server(s) sharing it. The other
concurrently-running Riverline dev server on this machine (port 3900,
`scripts/test-admin.mjs`'s dedicated server) was checked and is healthy.

Once I recognized the shared-`.next` collision as a real risk (regardless
of the port-3000 misdiagnosis), I stopped running a second `next dev`
against the main tree and instead followed the same-day precedent already
set by `docs/journal/2026-08-18-v2-email.md` ("Running Playwright against
the live shared working tree produced a 100%-reproducible false failure...
reproduced the identical run against an isolated `git worktree`"): created
`../riverline-v3-verify`, a `git worktree` pinned to `HEAD`, copied this
session's actual changed/untracked files into it (not just my own — the
full current working-tree state, so nothing from concurrently-running
agents was reverted in the copy), ran `pnpm install` there (fast — pnpm's
content-addressable store mostly linked, ~30s), and ran the dev server +
all verification entirely inside that isolated directory on port 4300.
Left the worktree in place (`../riverline-v3-verify`, outside the repo)
for now in case the verification needs re-running; it was `git worktree
add`ed directly (same as V2's approach), not via the harness's isolation
tooling.

## Deviations from the task brief

1. **Directional back-navigation isn't truly directional.** `.pageEnter`
   always slides in from the "forward" direction (`translateX(16px) → 0`)
   because a plain `<Link>` doesn't know whether a navigation is forward
   or back, and wiring true direction-awareness safely requires touching
   shared router/layout code that other agents are concurrently editing —
   out of scope for a CSS-and-component-styles motion pass. Documented
   honestly in `docs/design/motion.md`.
2. **Native View Transitions API not wired up**, despite verifying it's
   viable (iOS Safari 18+ has full single-document support per caniuse,
   and iOS 18 shipped September 2024 — the large majority of field
   iPhones are past that floor by August 2026). Same reasoning as #1: doing
   it correctly means intercepting navigation at `app/layout.tsx`/
   `app/AppShell.tsx`, shared files under concurrent edit. Flagged in
   motion.md as a good low-risk follow-up (a browser API, not a new
   dependency).
3. **`pnpm test:offline` status is genuinely unresolved** at the time of
   writing — see "Open items."
4. Touched `app/layout.tsx` for the iOS `:active` fix, which is arguably
   outside the literal "CSS module files + src/shared/ui" path list — did
   it anyway because the fix is a one-line, non-visual, additive `useEffect`
   registered the same way `RegisterServiceWorker` already is, and it's
   the only correct place for a document-root touch listener to cover both
   the shelled app and the shell-less capture flow. If this should have
   been a stop-and-ask, flagging it here.
