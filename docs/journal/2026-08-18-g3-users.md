# 2026-08-18 — T-G3: team user management (no-email onboarding)

## The gap

Before this task, the only way to create a `users` row anywhere in this
codebase was `scripts/db/seed.mjs`. An emergency manager standing up a new
jurisdiction had no way to onboard an inspector, a reviewer, or a second
administrator. This was the top emergency-readiness blocker.

## What I built

- **`/admin/users`** (admin-only, tenant-scoped): lists every user in the
  jurisdiction (email, role, created date, active/deactivated state), an
  "Add a team member" form (email + role only — AGENTS.md rule 8, no
  password field exists anywhere), inline role change per row, and
  deactivate/reactivate with a confirmation dialog on deactivate.
- **`migrations/0007_users_deactivated.sql`** — additive: `users.deactivated_at
  timestamptz null` + an index on `(jurisdiction_id, deactivated_at)`.
  Nullable, no backfill (every existing row is active by construction).
  Never deletes a user — history (assessments captured, determinations
  adopted, audit rows) stays attributable.
- **The no-email onboarding path** (the headline feature): creating a user
  makes them immediately magic-link-eligible — that IS the allowlist model
  (`requestMagicLink` refuses unknown emails). Since production has no
  configured email transport yet (`docs/BLOCKERS.md` B4), the admin can
  click "Create sign-in link" on any active user's row to mint a real,
  single-use, 24-hour token on demand (`src/core/auth/magic-link.ts`
  `issueSignInLinkForUser`, same `login_tokens` table + crypto primitives
  as a real magic link) and gets back a URL to hand to that person over any
  channel (text, phone, in person). It authenticates through the exact same
  `/api/auth/verify` route a real magic link uses. Rate-limited (10/15min
  per acting admin, 30/15min per IP — `app/api/admin/users/[userId]/
  sign-in-link/route.ts`, reusing `src/shared/security/rate-limit.ts`).
  Never logs the raw token; `audit_log.after_json` records only the email
  and expiry.
- **Guard rails**: an admin cannot deactivate or change the role of their
  own account (`cannot_act_on_self`); the last active admin of a
  jurisdiction can never be deactivated or demoted away from `admin` by
  anyone (`last_admin`, checked independently of the self-guard as
  defense in depth). Every mutation (create, deactivate, reactivate,
  change_role, generate_sign_in_link) writes `audit_log` with before/after.
- **`requireActiveRole`** (new, additive export in `src/core/auth/
  role-guard.ts`): same role check as the existing `requireRole`, plus a
  live DB check that the session's user has not been deactivated since the
  cookie was issued. Used by every G3 route/page. See "Scope of the
  deactivation-kicks-out guarantee" below for why this is additive, not a
  change to `requireRole` itself.
- **Readiness panel**: `/admin` now shows "Team: N active users (M
  assessors, K officials)" with a link to `/admin/users`
  (`src/core/admin/queries.ts` `getTeamSummary`, wired into
  `getReadinessStatus`).

## A real bug found and fixed: client bundle vs. `pg`

Running the e2e gate for real surfaced a genuine build-breaking bug, not a
test-authoring issue: `app/admin/users/_components/AddUserForm.tsx` and
`UserRow.tsx` (both `"use client"`) originally imported `ROLES`/
`ROLE_DESCRIPTIONS` from `@/core/admin`. That barrel (`src/core/admin/
index.ts`) also re-exports `queries.ts`/`actions.ts`, which import
`src/shared/db` → the `pg` driver. `pg-connection-string` unconditionally
`require('fs')`, which does not exist in a browser bundle — so importing
ANY runtime value from `@/core/admin`, even an unrelated one, broke the
client build with `Module not found: Can't resolve 'fs'` (discovered via
the actual `pnpm test:users` dev-server output, not a hunch).

Fix: moved the client-safe pieces (`ROLES`, `UserRole`, `ROLE_DESCRIPTIONS`)
to a new file, `src/shared/roles.ts` — zero-I/O, zero server dependency.
`src/shared/**` is a leaf under `eslint-plugin-boundaries`'s rules (no
`index.ts`-only restriction the way `src/core/*` has), so `app/*` can
import it directly. `src/core/admin/index.ts` re-exports the same values
from there for server-side consumers, so there is exactly one definition.
`UserListRow` (a type, not a value) stays imported from `@/core/admin` via
`import type` in the client components — fully erased at compile time, so
it never reaches the client bundle. No other core family had a prior
client component importing from its barrel, so this specific failure mode
had never been exercised before.

## A second real bug found and fixed: success-message race

`AddUserForm`'s submit handler called `setSuccessEmail(...)` and
`router.refresh()` in the same synchronous tick. In testing this appears to
have let React batch the state update and the refresh-triggered re-render
into one commit, so the "X was added and can now sign in" confirmation
never painted before the fresh server data replaced it (proof: after
submit, the row existed in the table with the right role, but the success
banner never appeared and the form's role selector had reverted to its
default — the form state was overwritten, not just the banner missed by a
race). Fixed by deferring `router.refresh()` one tick
(`setTimeout(() => router.refresh(), 0)`), so the success paint commits
first. This is a real UX fix, not just a test workaround — the task
requires the success state to "say plainly what happens next," and it
could not do that if it never became visible.

## Scope of the deactivation-kicks-out guarantee

Sessions in this codebase are stateless, signed cookies (`src/core/auth/
session.ts`, no DB-backed session store). ~40 existing pages/routes across
every other agent's module call `requireRole` synchronously. Making
`requireRole` itself async (to add a DB deactivation check) would silently
break every one of those call sites' typecheck without touching their
files directly — worse than not fixing it. Instead, `requireActiveRole` is
a new, additive export; only G3's own surfaces (`/admin/users`, the
`/api/admin/users/*` routes, and `/admin` itself, since the task explicitly
asked for the readiness-panel edit) use it.

Two things ARE proven, end to end:
1. A deactivated user's account can **never sign in again**, from any
   entry point (self-requested magic link or an admin-generated invite
   link) — `requestMagicLink` silently refuses to issue a token, and
   `verifyMagicLink` refuses to complete even an already-issued,
   unexpired token. This is universal, not scoped to G3's routes.
2. A deactivated user's **already-open session** is rejected on its next
   request to any G3-guarded route (`requireActiveRole`) — proven both at
   the unit level (`test/unit/admin/users-persist.test.ts`, directly
   against a deactivated session) and end-to-end in `test/e2e/users.spec.ts`
   (a still-logged-in second browser context reloading `/admin/users`
   after being deactivated gets redirected to `/login`).

What is NOT proven, and is an honest, documented gap: a deactivated user's
already-open session on a page owned by another agent (e.g. `/home`,
`/registry`) is not forcibly terminated mid-session by this task — it
naturally expires within the existing 12-hour session TTL, or the moment
they hit a G3-guarded route. Extending `requireActiveRole` to every route
in the app is future integration work for whoever owns that global rollout
(a mechanical swap of `requireRole` → `requireActiveRole` per route, now
that the helper exists), not something this task could safely do without
touching every other agent's files.

## Cross-tenant enforcement: `not_found`, not a distinguishing `403`

The task brief said "cross-tenant 403." This codebase's existing IDOR
precedent (`test/unit/security/photo-idor.test.ts`, proven against
`app/api/photos/[id]/route.ts`) treats a cross-tenant id as **invisible**
— the row does not exist from that tenant's perspective — rather than a
distinguishing "exists but forbidden" response, specifically so a response
never leaks whether an id belongs to another tenant. `deactivateUser`/
`reactivateUser`/`changeUserRole`/`generateSignInLink` all follow the same
pattern (queried `and jurisdiction_id = $2`, backed by RLS as a second
layer) and return `not_found` (mapped to HTTP 404 by the route), matching
this codebase's own established security convention rather than inventing
a new one. Proven in `test/unit/admin/users-persist.test.ts`'s
cross-tenant tests for every mutation.
