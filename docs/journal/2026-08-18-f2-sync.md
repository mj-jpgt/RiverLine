# 2026-08-18/20 — F2: live sync failure, root cause and fix

## The report

Field user on the live app (https://river-line.vercel.app): completed an
assessment on a phone, got "Sync failed — will keep this queued until you
retry." simultaneously with "Saved on this device — syncing now." on the
complete screen. Local `pnpm test:offline` passed, so this had to be
deployment-environment-specific.

## Reproduction — two real, independent live bugs found

Set up: minted a real magic-link session directly in the live db for
`assessor@example.gov` (insert into `login_tokens`, GET
`/api/auth/verify?token=...`, keep the cookie), then POSTed realistic
payloads to the live app.

**Bug 1 — Vercel's request body limit.** Built 8 real (not synthetic-flat)
JPEGs via Playwright's own Chromium canvas with per-pixel random noise
(worst-case-incompressible, ~1.27MB each at 1600×1200 quality 0.82 — the
same downscale `photo.ts` already does), then POSTed a payload with 3 of
them (2 element photos + 1 exterior) to `/api/capture/sync`:

```
Payload: 3 photos, body size = 4.86 MB
SYNC STATUS: 413
SYNC BODY: Request Entity Too Large / FUNCTION_PAYLOAD_TOO_LARGE
```

That `FUNCTION_PAYLOAD_TOO_LARGE` text is Vercel's own platform error page —
the request never reached this app's route handler at all. Vercel enforces
a hard ~4.5MB body ceiling per serverless invocation, independent of and far
below this app's own `MAX_SYNC_BODY_BYTES` (48MB) check, which never got a
chance to run. A dozen-element assessment with several detailed interior
photos crosses this routinely — this is the architectural root cause the
task brief's prime suspect #1 named, confirmed with a real repro, not a
guess.

**Bug 2 — a UTF-8 BOM in the Vercel `STORAGE_DRIVER` env var, and its
siblings.** Even a *single*-photo payload (1.62MB, nowhere near the 4.5MB
ceiling) came back `500 {"error":"Sync failed. It will remain queued and
retry."}`. `npx vercel logs` showed the real server-side exception:

```
[capture] sync failed: Error: Unknown STORAGE_DRIVER "﻿supabase". Expected "local" or "supabase".
```

That leading character between the quote and `supabase` is U+FEFF, a
byte-order mark — 65279 in decimal, confirmed later by a second exception
after fixing the first (`SUPABASE_SERVICE_ROLE_KEY` had the same corruption:
`Cannot convert argument to a ByteString because the character at index 0
has a value of 65279`, thrown by the Supabase SDK trying to use the key as
an HTTP header value). `STORAGE_DRIVER=supabase`'s switch-statement `case
"supabase"` never matched the BOM-prefixed value, so `getStorageDriver()`
threw on every single photo write, in every environment where any assessment
had at least one photo — independent of size. This is almost certainly the
bug hit most often in the field (bug 1 needs several sizeable photos; bug 2
breaks the very first photo of any size). Root cause: the env vars were set
via a `vercel env add` invocation piped from a source that defaulted to
UTF-8-with-BOM (this tool's own PowerShell guidance calls out `Out-File`/
`Set-Content`'s default-BOM behavior as exactly this trap).

**Live fix applied immediately** (`STORAGE_DRIVER`, `SUPABASE_SERVICE_ROLE_KEY`,
`NEXT_PUBLIC_SUPABASE_URL`, `STORAGE_BUCKET` — the whole batch, all set in
the same original session and all suspect): removed and re-added each via
`vercel env rm` / `vercel env add ... --value <clean literal>` (the
`--value` flag sidesteps any pipe/file that could reintroduce a BOM),
redeployed, and re-verified: a single-photo sync payload that previously
500'd now returns `200 {"ok":true,"assessmentId":"...","alreadySynced":false}`.

Also hardened `src/shared/storage/index.ts` (`getStorageDriver`) and
`src/shared/storage/supabase.ts` (`createSupabaseStorageDriver`) to
`.trim()` every env var read — `String.trim()` strips U+FEFF along with
ordinary whitespace per the ECMAScript spec, so a future env var edit that
reintroduces a stray leading/trailing character degrades to the value it
looks like instead of a silent full storage outage.

## The fix — per-photo upload, gated finalize

Per the task brief's prescribed shape: photos now upload **individually**,
before the draft's own sync payload:

- **`app/api/photos/upload/[id]/route.ts`** (new) — one photo's raw binary
  bytes (not base64 — buys back the ~33% encoding tax against Vercel's fixed
  ceiling), auth/tenant/rate-limit pattern copied from
  `app/api/capture/sync/route.ts`, magic-byte sniffing reused from
  `src/shared/security/upload-validation.ts` (`sniffImageType`), sha256
  re-verified against the actually-received bytes (never trusts the
  client's claim), content-addressed storage key
  (`<jurisdictionId>/<sha256>.jpg>`, same scheme as before —
  `docs/adr/0008-object-storage.md`). A local `MAX_PHOTO_UPLOAD_BYTES = 4MB`
  ceiling (not the shared `MAX_PHOTO_BYTES` — see the "what I deliberately
  did not touch" note below) leaves ~700KB of headroom under Vercel's ~4.5MB
  limit for a single raw-binary request.
- **`src/core/capture/photo-upload.ts`** (new) — `uploadPhoto`/
  `uploadPendingPhotosForDraft`: per-photo retry/backoff (reuses
  `backoff.ts`'s `backoffDelayMs`, same shape as the existing draft-level
  policy), sequential (not parallel — same "predictable load on a weak
  connection" reasoning `syncAllQueued` already used), idempotent by
  construction (content-addressed key), durable per-photo state so a
  killed-and-reopened queue resumes only the photos not yet confirmed.
- **`src/core/capture/types.ts`** — `PhotoRecord` gains
  `uploadStatus`/`uploadAttempts`/`lastUploadError`/`lastUploadAttemptAt`
  (`newPhotoUploadState()` factory, so the shape stays centralized).
  `src/core/capture/db.ts` gains `markPhotoUploadAttempt`/
  `markPhotoUploaded` (mirrors the existing draft-level
  `markSyncAttempt`/`markSynced`) and a `withUploadStateDefaults` migration
  shim so a photo captured before this feature existed reads back safely
  (defaults to "pending", never wrongly "uploaded").
- **`src/core/capture/sync.ts`** — `syncOne` is now two phases: (1) upload
  every pending photo for the draft, reporting live progress via a new
  `onPhotoProgress` callback; (2) only once every photo reports "uploaded"
  does the metadata-only finalize payload go to `/api/capture/sync`. A
  draft with photos still pending never reaches phase 2 — it returns a
  real, visible error ("N of M photos still need to upload"), and the next
  attempt (automatic or manual) resumes exactly where it left off.
- **`src/core/capture/payload.ts`** / **`app/api/capture/sync/route.ts`** —
  the wire payload dropped `dataBase64`/`contentType` entirely (metadata
  only: id/elementCode/sha256/capturedAt/gps). The finalize route no longer
  writes photo bytes; for each referenced photo it now computes the same
  deterministic storage key and calls `getStorageDriver().exists(...)` to
  confirm the upload actually happened before creating the `photos` row —
  never trusting the client's say-so. Body-size guard on this route dropped
  from the shared 48MB constant to a locally-defined 2MB (the payload is now
  a few KB regardless of photo count).

### What I deliberately did NOT touch

`src/shared/security/upload-validation.ts`'s shared `MAX_PHOTO_BYTES` (8MB)
and `MAX_SYNC_BODY_BYTES` (48MB) are also used by
`src/modules/a4-estimates/actions.ts` and its own upload route, with their
own, unrelated size budget. Lowering those shared constants for F2's own
transport-specific need would have silently tightened a4-estimates' limits
too. Instead, `app/api/photos/upload/[id]/route.ts` and
`app/api/capture/sync/route.ts` each define their own local, narrower
constant. Both files' comments cross-reference this reasoning.

## The contradictory-copy bug — fixed at the source

`app/capture/[id]/CaptureFlow.tsx`'s complete screen had its own separate
`draft.syncStatus === "synced" ? ... : online ? "syncing now" : "offline"`
chain that **never checked `syncError` at all** — so a real sync failure
(the `OfflineBanner` above it correctly showing "Sync failed") could sit
right next to "Saved on this device — syncing now." at the same instant.
Exactly the reported bug.

Fix: one `completeSubheading` expression, built from the *same* state
(`syncError`/`syncing`/`online`/`photoProgress`) that already drives
`bannerState` for the banner above it — a real error always wins and is
never masked by a stale "syncing now" claim. Added live "uploading photo N
of M" text (both banner and complete screen) via a new `photoProgress`
callback threaded from `sync.ts`. New copy is plain language, no em dashes,
per the standing directive (`Offline — N assessments queued` → `Offline. N
assessments queued.`, etc., only on the lines this task touched).

### Debugging `pnpm test:offline`'s own flakiness

The rewritten offline spec's new §10 (kill-mid-photo-upload-resume probe)
was genuinely flaky in this specific sandboxed dev machine, root-caused via
the failing runs' own trace.zip network logs (`playwright show-trace`'s
`0-trace.network`): intermittent, unexplained full-document `GET
/capture/[id]` navigations mid-test, aborting in-flight requests
(`Execution context was destroyed, most likely because of a navigation`).
Grepped this app's own code (`app/`, `src/`) for any `location.reload`/
router-refresh path that could explain it — none exists. This machine was
independently observed to be under severe, sustained memory pressure for
this entire session (as low as ~180MB free of 16GB, "Memory Compression"
process alone using 1.3GB, five concurrent Cursor windows, two other Claude
Code sessions, Docker, WSL all running at once) — consistent with
Chromium's own background-tab throttling/discarding kicking in on an
automated tab that doesn't hold real OS focus. Added the standard
counter-flags to `playwright.offline.config.ts`'s chromium project
(`--disable-background-timer-throttling`,
`--disable-backgrounding-occluded-windows`, `--disable-renderer-backgrounding`,
`--disable-ipc-flooding-protection`) — these only change automation-host
scheduling, never real device/app behavior — and the failure mode stopped
reproducing (3/3 clean runs afterward, down from ~15-50s of flailing to a
consistent 15-35s). Also made the spec itself more resilient regardless of
root cause: `expect.poll` callbacks that read IndexedDB now catch and
retry rather than aborting the whole poll on one bad tick (`expect.poll`,
unlike `.toPass()`, does not catch its own callback's exceptions), and the
online-transition "nudge" logic was changed from a tight repeated
click/dispatch retry loop to at-most-two widely-spaced triggers (a tight
retry loop was itself empirically correlated with triggering the stray
navigation, independent of the throttling fix).

The new §10 proves, against the real endpoint (no mocks): a first sync pass
that partially fails (one pre-chosen photo's upload made to fail once, the
rest succeed) survives a real kill/reload with the successful photos'
`uploadStatus` durably intact (read straight out of IndexedDB after reload,
no network call needed); a resumed sync retries only the photo that
actually failed (asserted via the upload-request log: the failed photo
shows ≥2 requests); and the reported live bug directly — the banner and the
complete screen's subheading are asserted to never show the "syncing now" +
"failed" contradiction at once.

## Live verification (env-var fix only — architecture NOT re-verified live)

Per an explicit orchestrator instruction partway through this task ("Do NOT
do any mutating verification against the live production database or the
live site; live checks are read-only only"), further live POST-based
reproduction was stopped once that instruction arrived. What *is* verified
live, from before that instruction:

- `STORAGE_DRIVER`/`SUPABASE_SERVICE_ROLE_KEY`/`NEXT_PUBLIC_SUPABASE_URL`/
  `STORAGE_BUCKET` BOM fix: deployed and confirmed — a single-photo sync
  payload POSTed to the live `/api/capture/sync` went from `500` to `200`
  with a real `assessmentId`.
- The 413 body-limit bug: confirmed live, motivating the architecture
  redesign in this same commit.

**Not yet re-verified live**: the new per-photo-upload architecture itself
(`/api/photos/upload/[id]` + the metadata-only finalize payload) has not
been exercised against the live deployment after this commit, since doing
so would require further live-mutating POSTs the orchestrator's later
instruction disallows. It is verified thoroughly locally (3 consecutive
green `pnpm test:offline` runs against a real production build, real
Postgres, real Supabase-driver-shaped storage calls — `STORAGE_DRIVER`
defaults to `local` in dev/test, unchanged from before this task) and via
direct code review of the auth/tenant/validation pattern, which is copied
verbatim from the already-live-proven `/api/capture/sync` route. Whoever
picks this up next should re-run the live reproduction (a throwaway
`.scratch-f2/repro-sync-v2.mjs` was written for exactly this — upload N
photos individually, then finalize, against `river-line.vercel.app`,
practice-structure `123 Practice Ln` clientId prefixed `f2-repro-v2-`) once
live mutation is re-authorized, and confirm: individual `POST
/api/photos/upload/[id]` calls return 200, the finalize call succeeds
referencing them, and the photos/storage rows are real.
